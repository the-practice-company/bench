# baton — дизайн плагина для многодневных автономных прогонов

**Дата:** 2026-08-03
**Статус:** согласован в brainstorming, ожидает вычитки
**Входные документы:** проектный брифинг, отчёт «Managing Multi-Day Autonomous Claude Code Sessions», отчёт «State and Artifact Architecture»

---

## 1. Проблема

Агент работает над задачей несколько дней в одной сессии Claude Code. Контекст периодически обнуляется — автоматически или по команде человека. После обнуления агент теряет понимание того, где он находится, что уже сделано и кем он является в этом прогоне.

Сегодня это лечится вручную: человек несколько раз в день печатает две повторяющиеся фразы —

1. «проверь, всё ли легло в персистентные файлы, ничего ли не потеряем при компакте»;
2. «ты только оркестратор, работу делегируешь агентам и workflows, твоя обязанность — качественно довести всё до конца».

**Критерий готовности v1:** обе фразы перестают печататься руками. Всё остальное — бонус.

Формулировка задачи: агент, проснувшийся после обнуления контекста на третий день, за один шаг восстанавливает корректное понимание «где мы, кто я, что дальше» — и это понимание **проверяемо**, а не вспомнено.

## 2. Чем это не является

- **Не трекер задач.** Уровень волн — таблица в `state.md`, уровень задач внутри волны — чекбоксы в плане Superpowers. Третьего слоя нет.
- **Не memory-система.** Ни векторов, ни эмбеддингов, ни семантического поиска. Состояние маленькое и читается целиком.
- **Не оркестратор.** Плагин даёт протокол работы с состоянием, а не механику запуска воркеров.
- **Не форк Superpowers.** Только композиция рядом.
- **Не замена brainstorming.** Спеки и планы волн по-прежнему пишет Superpowers, в свои места.

## 3. Аудитория и решения, принятые на входе

| Решение | Выбор |
|---|---|
| Аудитория | Публичный плагин с самого начала. Никаких предположений про Linear, Twinkle или чужой стек — только git и файлы. |
| Владение состоянием | Владелец — роль, а не процесс. Бессмертного оркестратора нет; любая primary-сессия берёт роль писателя под замком, компактится, восстанавливается из состояния и продолжает. |
| Расхождение состояния и репозитория | Политика по измерениям: наблюдаемое (SHA, ветка, чистота дерева) чинится молча; заявленное (волна = done) не чинится никогда, помечается `suspect` и выносится наверх. |
| Скоуп v1 | Четыре вещи: чекпойнт, состояние, журнал, гейт. |
| Провал гейта | Задача агента — починить. Эскалация только когда агент застрял. |
| Имя | `baton` — дирижёрская палочка и эстафетная одновременно. |
| Основа принуждения | Проза первична (плагин должен работать в любом репозитории), скрипты точечно — на репо-независимой механике. |

## 4. Отношения с Superpowers

Superpowers закрывает **одну единицу работы** от начала до конца. baton закрывает то, что **над** и **между** этими единицами на дистанции в несколько дней.

| Что | Владелец |
|---|---|
| Umbrella-дизайн и дизайны волн | Superpowers `brainstorming` → `docs/superpowers/specs/` |
| Планы волн | Superpowers `writing-plans` → `docs/superpowers/plans/` |
| Исполнение волны | Superpowers `subagent-driven-development` / `executing-plans` |
| Конституция: цель прогона, режим работы, разбиение на волны, полномочия | baton |
| Где мы сейчас, кто я, что оборвалось, что дальше | baton |
| Журнал решений | baton |
| Гейт на границе волны | baton |

`state.md` ничего не дублирует — он хранит **указатели** на артефакты Superpowers.

**Факт, проверенный при проектировании:** в Superpowers 5.1.0 нет durable-ledger в `.superpowers/sdd/` (утверждение из входного отчёта не подтвердилось — прогреплена установленная версия). Прогресс там держится на чекбоксах `- [ ]` в файле плана и на TodoWrite в контексте. TodoWrite умирает при обнулении контекста, чекбоксы никто не сверяет с репозиторием. Дыра реальна и незакрыта.

**Механика связи.** Формального поля `dependencies` в `plugin.json` не существует (проверено на 40 установленных плагинах). Связь делается через marketplace: наш `marketplace.json` перечисляет два плагина — `baton` из этого репозитория и `superpowers` ссылкой на `obra/superpowers`. Пользователь добавляет один marketplace и ставит оба. `/baton:init` проверяет наличие Superpowers и предупреждает, если его нет.

**Что берём по форме.** Superpowers — образец того, как писать такую надстройку: `skills/<name>/SKILL.md` с frontmatter, где `description` начинается с «Use when…»; graphviz-диаграммы процесса прямо в скиле; таблица «Red Flags» вида «мысль агента → почему это рационализация»; companion-файлы `*-prompt.md` для запуска субагентов; явные перекрёстные ссылки на другие скилы.

## 5. Иерархия принуждения

Главная архитектурная ось. Чем критичнее инвариант, тем ниже по таблице он живёт.

| Уровень | Механизм | Что сюда кладём |
|---|---|---|
| Принудительный | скрипты, git | атомарность записи, факты из репозитория, запуск проверки, поиск заглушек, замок |
| Полупринудительный | хуки Claude Code | снятие фактов до обнуления контекста, указание на подъём после |
| Совещательный | скилы, команды | процедуры, суждение, объяснение «зачем» |

Проза первична как источник **процедуры и суждения**, потому что плагин должен работать в любом репозитории и не может знать, как устроен конкретный проект. Скрипты несут только ту механику, которая обязана быть повторимой и репо-независимой.

**Асимметрия полномочий** — то, что делает прозаическую основу безопасной. Подробности в разделе 8.

## 6. Раскладка артефактов

Следуем конвенции Superpowers: на виду, в `docs/`, коммитится, а не прячется в дотфолдер. Это же обслуживает требование «одно место, куда человек смотрит первым».

```
docs/
  superpowers/
    specs/                  ← brainstorming: umbrella-дизайн и дизайны волн
    plans/                  ← writing-plans: планы волн
  baton/
    constitution.md         ← ратифицирует человек; агент не пишет
    state.md                ← живое состояние, единственный писатель
    journal/
      0001-<slug>.md        ← append-only
    gates/
      <wave>-<sha>.md       ← протоколы гейтов
.baton/                     ← машинное, целиком в .gitignore
  lock
  precompact-facts          ← пишет хук PreCompact, читает подъём
```

Путь по умолчанию переопределяется пользовательскими настройками — тот же принцип, что у Superpowers.

### 6.1. `docs/baton/constitution.md`

Пишет человек, ратифицирует человек, агент только читает. Имя выбрано намеренно: «конституция» несёт коннотацию неприкосновенности сильнее, чем «спека».

```markdown
---
schema: baton/constitution/v1
run_id: <slug>
status: ratified                 # draft | ratified
ratified_by: <человек>
ratified_at: <ISO8601>
git_anchor: <SHA на момент ратификации>
umbrella_spec: docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md
verify_cmd: "npm test"
placeholder_patterns: "TODO|FIXME|NotImplemented|unimplemented|raise NotImplementedError"
---

# <Название прогона>

## Goal
Что считается успехом всего прогона. Одно-два предложения.

## Operating mode
Кто агент в этом прогоне. Дефолт: оркестратор — делегирует реализацию субагентам
и workflows, сам не пишет код в primary-сессии, отвечает за доведение работы до конца.

## Non-negotiables
Правила, которые нельзя нарушить ни в одной волне.

## Waves
- wave: 1
  name: <имя>
  depends_on: []
  parallel_with: []
  exit_criteria:
    - The system shall <проверяемое поведение>
- wave: 2
  name: <имя>
  depends_on: [1]
  parallel_with: [3]
  produces:                      # обязательно, если parallel_with непусто
    - <контракт, который волна публикует наружу>
  consumes:
    - <контракт, который волна берёт из upstream>
  exit_criteria:
    - When <триггер>, the system shall <проверяемое поведение>

## Decision authority
Что агент решает сам, что выносит человеку.

## Amendments
Только дописывание. Каждая поправка: дата, что изменилось, кто ратифицировал.
```

**Почему `verify_cmd` живёт здесь, а не в отдельном конфиге.** Если агент может править конфиг гейта, он может ослабить гейт — и тогда гейта нет. Конституцию агент не пишет, значит порог проверки он подвинуть не может. Это свойство безопасности, а не аккуратности.

**`exit_criteria` пишутся в EARS** — пять шаблонов с обязательным «shall»: `The system shall…` (всегда), `When <триггер>, the system shall…` (событие), `While <состояние>, the system shall…`, `Where <фича включена>, the system shall…`, `If <условие>, then the system shall…` (нежелательное поведение). Формат обязателен, потому что суждение гейта опирается именно на эти строки: критерий, допускающий два прочтения, — это критерий, который агент прочитает в свою пользу.

**`produces` / `consumes` требуются только для волн с непустым `parallel_with`.** Параллельность безопасна, только если контракт объявлен **до** реализации: иначе две волны, идущие одновременно, договариваются об интерфейсе постфактум и сталкиваются. Для последовательных волн эти поля — лишняя церемония, и их не требуем.

### 6.2. `docs/baton/state.md`

Единственный писатель — сессия, держащая замок. **Жёсткое ограничение: не длиннее 60 строк.** Длиннее — сломан, лишнее уезжает в журнал. Число выбрано как «влезает на один экран целиком», и оно проверяемо, в отличие от «держи файл компактным».

```markdown
---
schema: baton/state/v1
writer: <session-id>
updated_at: <ISO8601>
observed_sha: <SHA>
observed_branch: <ветка>
tree_clean: true
suspect: false
needs_human: false
---

# State

**Goal:** одна строка, скопированная из конституции
**Operating mode:** одна строка, скопированная из конституции
**Non-negotiables:** список из конституции, дословно

## Waves
| # | name | status | branch/worktree | spec | plan | closed_at_sha | gate |
|---|------|--------|-----------------|------|------|---------------|------|
| 1 | auth | done   | wave-1-auth     | docs/superpowers/specs/2026-08-01-auth-design.md | docs/superpowers/plans/2026-08-01-auth.md | a1b2c3d | pass |
| 2 | api  | doing  | ../wt-api       | docs/superpowers/specs/2026-08-02-api-design.md  | docs/superpowers/plans/2026-08-02-api.md  | —       | —    |
| 3 | ui   | todo   | —               | —                                                 | —                                          | —       | —    |

**Current wave:** 2 — api

## Now
- **Next action:** одно детерминированное предложение
- **In flight:** что оборвалось на середине, или "nothing"
- **Suspect:** в чём заявленное разошлось с репозиторием, или "none"
- **Open questions:** или "none"

## Pointers
- Constitution: docs/baton/constitution.md
- Recent decisions: docs/baton/journal/0007..0009
```

Статусы волны: `todo | doing | done | blocked`, где `blocked` означает «ждёт закрытия волны, от которой зависит».

Два флага во frontmatter — не статусы, потому что относятся к прогону целиком, а не к отдельной волне:

- `suspect` — заявленное в состоянии разошлось с репозиторием;
- `needs_human` — прогон остановлен, дальше без человека нельзя.

Слово `blocked` намеренно не используется для флага: статус волны и остановка прогона — разные вещи, и одинаковое имя для них порождало бы путаницу ровно в тот момент, когда её меньше всего можно себе позволить.

Дублирование `Goal`, `Operating mode` и `Non-negotiables` из конституции — осознанное, и каждая строка отрабатывает свою боль.

`Goal` и `Operating mode` снимают обе ручные фразы человека при подъёме, не заставляя читать конституцию целиком. `Non-negotiables` лечит goal drift — задокументированный отказ, при котором агент корректно выполняет текущий запрос, но нарушает правило из исходного брифа: «не трогай user model» → через три часа трогает. Митигация из исследования состоит из двух половин — восстанавливать при подъёме цель **и живые ограничения**. Одна половина без другой не работает.

Колонка `branch/worktree` нужна ровно на подъёме: если волна живёт в отдельном worktree (штатный паттерн, механику даёт `superpowers:using-git-worktrees`), после обнуления контекста агент иначе не узнает, в каком дереве шла работа. Механика чужая — указатель наш.

**Инвариант восстановимости.** Event sourcing требует, чтобы читаемое состояние было проекцией лога, которую всегда можно перестроить с нуля: удалить State, проиграть лог, получить то же самое. Без этого свойства набор файлов остаётся набором файлов, а не восстанавливаемой системой.

У нас инвариант выполняется, но лог — **не** `journal/`. Логом событий служит git: `state.md` коммитится при каждом чекпойнте, каждый коммит есть событие, а `git log -p docs/baton/state.md` даёт полную упорядоченную ленту. Удалить файл и перестроить его из истории можно всегда.

Разделение, которое стоит держать в голове, потому что слово «append-only» относится к обеим сущностям и склеивает их:

| | Лог событий | Лог решений |
|---|---|---|
| Где | история git `state.md` | `docs/baton/journal/` |
| Отвечает на | «где мы были в каждый момент» | «почему так решили» |
| Полнота | полная, ничего не фильтруется | отфильтрован порогом значимости |
| Восстановление State | да | нет, и не предназначен |

Журнал отфильтрован намеренно — журнал, который никто не читает, есть отдельный режим отказа. Именно поэтому нести на нём восстановимость нельзя, и её несёт git. Инвариант проверяется тестом 9.

### 6.3. `docs/baton/journal/NNNN-<slug>.md`

По файлу на запись, только дописывание. Запись **никогда не редактируется**: если решение отменяется, пишется новая со ссылкой, старая помечается `superseded-by`. Правда — вся цепочка, а не последняя запись.

```markdown
---
id: DEC-0007
type: decision              # decision | incoming | gate-failure | takeover
status: accepted            # accepted | superseded-by: DEC-NNNN
decided_by: agent           # agent | human
wave: 2
timestamp: <ISO8601>
sha: <SHA>
reversibility: two-way      # two-way | one-way
blast_radius: low           # low | medium | high
needs_review: false
---
## Context
## Options
## Decision
## Why
## Invalidated if
```

**Порог записи.** Пишем, только если выполнен хотя бы один пункт:

- решение трудно откатить;
- оно задевает что-то за пределами объявленного объёма текущей волны;
- оно переосмысляет правило из конституции;
- выбор был между реальными альтернативами, и проигравшая была правдоподобна.

Всё остальное не пишем. Журнал, который никто не читает — документированный режим отказа.

**Типы, отличные от `decision`,** имеют сокращённый набор секций:

- `incoming` — новая вводная от человека посреди прогона. Секции: Context, What changed, Impact. Всегда `needs_review: true`.
- `gate-failure` — провал гейта. Секции: Fingerprint, What failed. Пишется скриптом.
- `takeover` — перехват протухшего замка. Секции: Previous writer, Why taken.

### 6.4. `docs/baton/gates/<wave>-<sha>.md`

Улики, а не мнение. Пишется скриптом, дополняется агентом.

```markdown
---
schema: baton/gate/v1
wave: 2
sha: <SHA>
verdict: fail               # pass | fail
mechanical: fail            # pass | fail
judgment: not-run           # pass | fail | not-run
fingerprint: 3f9a1c04
timestamp: <ISO8601>
---
## Verify command
`npm test` → exit 1, 43s
## Failing
<хвост вывода>
## Placeholders found
src/api/handler.ts:88 — TODO
## Tree
dirty: 3 files
## Judgment notes
<заполняет агент>
```

Инварианты:

- `verdict: pass` **только** если `mechanical: pass` и `judgment: pass`;
- `judgment: not-run` возможно только при `mechanical: fail` — суждение не запускается, когда механика уже провалила гейт.

## 7. Поверхности плагина

Основной потребитель — агент в автономном прогоне. Человек участвует в трёх точках: проектирование, ратификация, утренний взгляд. Поверхности распределены соответственно.

### 7.1. Скилы — основная поверхность

| Скил | Когда срабатывает |
|---|---|
| `baton` | начало работы в репозитории, где есть `docs/baton/`; объясняет модель: что авторитетно, что производное, почему |
| `baton-checkpoint` | перед обнулением контекста, перед завершением рабочего отрезка, после закрытия значимого куска |
| `baton-resume` | после обнуления контекста, при потере понимания «где я» |
| `baton-gate` | закрытие волны |

Описания скилов пишутся настойчиво, с явным перечислением контекстов срабатывания — известное свойство скилов не срабатывать, когда должны, для процессных скилов критично.

### 7.2. Команды — только человеческие точки входа

| Команда | Кто и когда |
|---|---|
| `/baton:init` | человек, один раз при заводке прогона |
| `/baton:checkpoint` | человек, перед тем как вручную дёрнуть compact |
| `/baton:status` | человек, утренний взгляд «где всё и не пора ли вмешаться» |

`/baton:resume` как команды нет — подъём автоматический, через хук и скил.

### 7.3. Хуки — ставятся по умолчанию

| Хук | Что делает |
|---|---|
| `PreCompact` | снимает факты из git в `.baton/precompact-facts` и предупреждает агента, что чекпойнт не сделан |
| `SessionStart` (matcher `compact`) | подаёт указание на подъём плюс строки `Goal`, `Operating mode` и `Next action` из состояния |

**`PreCompact` не пишет в `state.md`.** Единственный писатель состояния — сессия под замком, и хук не имеет права его подменять. Если бы он молча обновлял наблюдаемые поля, он стирал бы ровно то расхождение, которое обязано было всплыть как `suspect`. Вместо этого он складывает факты рядом, а `baton-resume` сравнивает их с состоянием и понимает, была ли работа между последним чекпойнтом и обнулением контекста.

Это же согласуется с известным ограничением: `PreCompact` физически не может заставить агента что-либо сделать — он только пишет на диск и предупреждает.

Хуки ничего не трогают за пределами плагина и `docs/baton/`. Ранее рассматривалась дописка блока в `CLAUDE.md` пользователя — отвергнута: лезть в чужой файл для публичного плагина неприемлемо, при удалении плагина остался бы мусор.

API хуков официально не помечен стабильным. Поэтому файл авторитетен, хуки вспомогательны, а скилы дублируют хуки: при полностью сломанных хуках прогон работает, просто менее удобно.

### 7.4. Скрипты — репо-независимая механика

Зависимости: `bash`, `git`, `sed`/`grep`/`awk`, `shasum`. Ничего больше.

| Скрипт | Что делает |
|---|---|
| `baton-observe` | печатает факты из git как `key=value`: SHA, ветка, чистота дерева, файлы изменённые с указанного SHA |
| `baton-write` | атомарная запись: временный файл → `fsync` → переименование. Коммитит `docs/baton/`. Если единственное отличие от закоммиченной версии — `updated_at`, **не пишет вовсе** и выходит с кодом 0 |
| `baton-verify` | читает `verify_cmd` и `placeholder_patterns` из frontmatter конституции; запускает проверку; грепает изменённые в волне файлы; проверяет чистоту дерева; пишет протокол гейта; код возврата = механический вердикт |
| `baton-lock` | взять / проверить / освободить / перехватить замок |

Ни один скрипт не знает ничего об устройстве конкретного проекта: всё специфичное приходит из конституции.

## 8. Протоколы

### 8.1. `/baton:init` — разговор, а не шаблон

Umbrella-спека должна изначально писаться под волновой процесс, а `brainstorming` этого не делает — он даёт спеку одной единицы работы. Поэтому `init` — отдельный диалог с человеком **после** brainstorming.

1. Найти umbrella-спеку в `docs/superpowers/specs/` (или спросить путь).
2. Проверить, что Superpowers установлен; если нет — предупредить.
3. Провести диалог о декомпозиции: что параллелится, где контракты между волнами, где риск, по каким проверяемым критериям волна считается закрытой.
4. Спросить команду проверки для этого репозитория (`verify_cmd`) и паттерны заглушек под язык проекта.
5. Записать `docs/baton/constitution.md` и `docs/baton/state.md`, добавить `.baton/` в `.gitignore`, закоммитить.
6. Попросить человека ратифицировать конституцию.

Декомпозиция — отдельный разговор со своей логикой, и смешивать его с проработкой требований значит делать оба хуже. Это третий вариант из брифинга, и он оказался несущим, а не опциональным.

### 8.2. Чекпойнт

1. `baton-observe` снимает факты из git.
2. Агент сверяет заявленное в состоянии с фактами. Наблюдаемые поля переписывает молча. Заявленные при расхождении **не чинит никогда** — ставит `suspect: true`, описывает расхождение в строке `Suspect` и выносит наверх.
3. Агент обновляет повествовательную часть: `Next action` одним детерминированным предложением, `In flight`, `Open questions`.
4. Решения с прошлого чекпойнта, прошедшие порог из 6.3, уходят в журнал.
5. `baton-write` пишет атомарно и коммитит.

Оборванная запись не может испортить файл.

**Состояния вне лога не существует.** После завершения чекпойнта `docs/baton/` чист по `git status` — всегда, без исключений. Отсюда следует, как именно устроен холостой прогон: если содержательного отличия от закоммиченной версии нет, `baton-write` **не трогает файл вообще**, а не пишет его с новой временной меткой и пропускает коммит. Второй вариант оставлял бы состояние изменённым в рабочем дереве, то есть вне лога, и ломал бы инвариант 6.2 ради косметики. Прогон команды дважды подряд поэтому безопасен и не оставляет следов.

**Две категории точек сохранения.** Теория checkpoint-restart различает координированные точки (все участники в глобально консистентном состоянии) и некоординированные (дешевле, но откат одного участника может потянуть каскад откатов остальных). У нас координированная точка одна — **граница волны**: гейт, тег, зафиксированный `closed_at_sha`. Чекпойнты между границами некоординированные и намеренно дешёвые.

Каскада при этом не возникает, и не потому что мы аккуратны, а по построению: параллельные волны живут ниже слоя состояния (раздел 9), временная линия состояния одна, и откатывать у соседей нечего.

### 8.3. Подъём

Агент не должен *помнить*, что надо восстановиться. Три независимых пути, по убыванию надёжности:

1. `docs/baton/state.md` лежит на диске и авторитетен всегда.
2. Хук `SessionStart(compact)` подаёт указание на подъём и три ключевые строки.
3. Скил `baton-resume` с описанием, настроенным на контексты «после обнуления контекста», «не понимаю, где я».

Процедура:

1. Прочитать конституцию и состояние.
2. `baton-observe`, сверить.
3. Прочитать `.baton/precompact-facts`, если он есть: работа между последним чекпойнтом и обнулением контекста означает, что состояние отстало.
4. Если `suspect: true` или `needs_human: true` — разбираться с этим **до** любой другой работы.
5. Иначе выполнять `Next action`.

Чтение дважды безопасно: при подъёме не происходит записей, кроме починки наблюдаемых полей.

**Правило против переделывания.** Прежде чем реализовывать что-либо после подъёма, агент обязан проверить, не существует ли это уже. Задокументированный отказ: агент грепает, не находит по ожидаемому имени, заключает, что не реализовано, и пишет заново — поверх работающего кода. Риск максимален именно на свежем контексте, где памяти о сделанном нет по определению.

Правило совещательное и лежит в `baton-resume` и в Red Flags скила `baton`. Механики под него не строим: цена ошибки — потерянное время, а не испорченное состояние, и она не оправдывает обязательного шага в каждом цикле.

### 8.4. Замок

`.baton/lock` — id сессии, pid, время. Чекпойнт отказывается писать, если замок держит другая живая сессия. Замок в `.gitignore` — он про машину, а не про репозиторий.

**Замок держится всю сессию, а не на время записи.** Это прямо следует из того, что писатель — роль: роль занимают, а не одалживают на каждую операцию. Берётся при первом чекпойнте или подъёме, освобождается при завершении сессии.

Замок на время записи выглядел бы аккуратнее, но не давал бы ничего: две сессии по очереди брали бы его и писали противоречащие друг другу состояния, каждая честно и без конфликта. Гонку он бы устранил, а расхождение — нет.

Протухшим считается замок с мёртвым pid либо старше шести часов. Перехват разрешён и пишется в журнал типом `takeover` — тихий перехват означал бы, что две сессии могли работать параллельно и никто об этом не узнал.

### 8.5. Гейт

Две части с асимметричными полномочиями.

**Механическая часть** (`baton-verify`): запускает `verify_cmd`, записывает код возврата, хвост вывода, длительность и SHA; грепает файлы, изменённые в этой волне, на `placeholder_patterns`; проверяет, что дерево чистое — незакоммиченная работа означает, что волна не закрыта.

**Часть суждения** (проза в скиле): агент оценивает, выполнены ли критерии на самом деле.

```
механика fail                          → гейт провален, суждение не спрашивается
механика pass + агент нашёл дыру       → гейт провален
механика pass + агент дыр не нашёл     → гейт пройден
```

**Проза может быть только строже, никогда мягче.** Единственное, что она способна сделать неправильно — придраться лишний раз. Это и делает прозаическую основу безопасной.

**Якорь суждения — `exit_criteria` из конституции, а не спека волны.** Спека волны может добавить критериев, но не может ослабить или переопределить ни одного из конституции. При расхождении выигрывает конституция.

Это не педантизм, а закрытие дыры, которую порождают два других наших решения. Спеки волн пишет агент, и человек их не ревьюит (раздел 9). Если бы гейт судил только по такой спеке, агент мог бы ослабить критерий и честно пройти проверку по ослабленному — реализация не подделана, подделан порог. Измеренная подверженность моделей игре против «испорченной» спеки — 50–70%. Конституцию агент не пишет, поэтому якорь в ней эту петлю разрывает.

**При успехе** гейт ставит аннотированный git-тег `baton/wave-<N>` на SHA закрытия. Бесплатная аттестация: закрытые волны становятся видимыми через `git tag` без чтения каких-либо файлов baton, и остаются видимыми, даже если состояние потеряно.

**При провале** волна остаётся в `doing` — отдельного статуса «на проверке» нет, в `done` она переходит только по пройденному гейту. В журнал пишется запись типа `gate-failure` с *отпечатком*: имена упавших тестов плюс найденные пары «путь:паттерн», отсортированные и свёрнутые в первые 8 символов `shasum`. Агент чинит и прогоняет снова.

Если один и тот же отпечаток повторился **три раза подряд** — агент в цикле. Состояние получает `needs_human: true`, в журнал пишется запись с `needs_review: true`, `/baton:status` это показывает. Это единственный случай, в котором гейт зовёт человека.

Отпечаток, а не счётчик попыток: три разных провала подряд — нормальная работа, три одинаковых — застревание.

### 8.6. Новые вводные посреди прогона

Конституция ратифицирована человеком и агент её не пишет, но реальность меняется.

Агент записывает новую вводную в журнал типом `incoming` с `needs_review: true`. Если она противоречит конституции — переводит затронутую волну в статус `blocked`, ставит `needs_human: true` и выносит наверх, а не решает сам. Поправку в раздел `Amendments` вносит человек.

### 8.7. `/baton:status`

Рендер для человека, тридцать секунд на понимание. Отклонения важнее прогресса:

1. `needs_human` и `suspect` — первым делом, если есть.
2. Записи журнала с `needs_review: true`, ещё не разобранные.
3. Текущая волна, `Next action`, `In flight`.
4. Таблица волн одной строкой каждая.

## 9. Полномочия и параллельность

**Ревью.** Человек ревьюит только umbrella-спеку и конституцию. Спеки и планы волн — только агентом. baton не имеет права ставить человеческие гейты на создании спеки волны.

**Границы автономии агента.** Агент свободно переписывает спеку и план волны. Агент **не** меняет границы волн, не добавляет и не удаляет волны, не правит конституцию — это через поправку от человека.

**Порог полноты информации.** Обратимое решение принимается примерно на 70% нужной информации, а не на 90%. Ожидание полноты в обратимом случае — это медленно, а не осторожно. Правило существует, чтобы автономный прогон не вырождался в поток эскалаций: человек просил чинить самому, и «мне не хватает данных» не должно становиться способом этого избежать. К необратимым решениям правило не применяется — там осторожность уместна.

**Параллельность.** Primary-сессия — оркестратор; реальная работа уходит в субагентов и workflows. Значит параллельные волны живут **ниже** слоя состояния: субагенты не пишут `state.md` вообще, оркестратор записывает результат, когда они вернулись. Один писатель сохраняется, шардировать состояние не нужно, гонок нет по построению.

Конституция объявляет граф зависимостей (`depends_on`, `parallel_with`) с самого начала — это ничего не стоит и нужно всё равно.

Не поддержан единственный случай: две независимые человеком запущенные сессии на одном репозитории. Их отвергнет замок — это правильное поведение, а не ограничение.

## 10. Бюджет контекста

Система не должна съесть то, что защищает.

- **Бюджет восстановления** = конституция + `state.md`. Целевой потолок — единицы процентов окна, и он **не растёт с числом волн**.
- **Правило указателей.** Состояние хранит пути и идентификаторы, а не содержимое.
- **Потолок состояния.** Длиннее 60 строк — сломан; лишнее вытесняется в журнал.
- **Тело скила** держим компактным; длинное выносим в `references/` с указателями.

Рост бюджета линейно с числом волн — сигнал, что конструкция не масштабируется, чинить до релиза.

## 12. Проверка

Не «выглядит ли разумно», а проверяемо. Автоматизируемые тесты:

1. **Холодный подъём.** Фикстура: репозиторий посреди волны. Убить сессию, поднять с нуля. Первое действие агента совпадает с `Next action`; человека не переспрашивает; сделанное не переделывает.
2. **Ложная готовность.** Фикстура: реализация — заглушка, состояние утверждает `done`. Гейт **обязан** провалиться. Если этот тест когда-либо пройдёт — гейт сломан.
3. **Бюджет.** Замерить стоимость восстановления в токенах на волне 1 и на волне 8. Не должна расти с числом волн.
4. **Деградация.** Хуки отключены. Всё работает через скилы и команды.
5. **Атомарность.** Убить запись на середине. `state.md` либо старый, либо новый, но не повреждённый.
6. **Замок.** Вторая сессия получает отказ. Протухший замок перехватывается с записью в журнал.
7. **Идемпотентность подъёма.** Двойное чтение состояния ничего не ломает.
8. **Срабатывание скилов.** По образцу `tests/skill-triggering` из Superpowers.
9. **Состояния вне лога нет.** После каждого чекпойнта — включая холостой, где менять нечего — `git status docs/baton/` чист. Затем удалить `state.md`, восстановить из истории и сверить побайтово. Проверяется инвариант 6.2, и проверяется именно наша половина: git и без нас умеет отдавать закоммиченное, а вот не оставить состояние в рабочем дереве — это уже поведение `baton-write`, и сломать его легко. Гоняется первым: пока тест зелёный, у нас восстанавливаемая система, как только красный — набор файлов.

Ручной критерий приёмки: реальный прогон длиной в три дня с несколькими обнулениями контекста. Метрика — сколько раз человеку пришлось вручную вправлять агенту понимание задачи. Целевое значение — ноль.

## 13. Режимы отказа самой конструкции

| Отказ | Митигация |
|---|---|
| Коллапс церемонии: ритуал тяжёлый → агент срезает → состояние протухает | Чекпойнт — один вызов. Частичное выполнение не хуже невыполнения (атомарность). |
| Ожирение состояния: растёт с каждой волной, перестаёт влезать в бюджет | Жёсткий потолок «один экран»; вытеснение в журнал; тест 3. |
| Журнал, который никто не читает | Порог значимости из 6.3; структурированные поля; выборка `needs_review` в `/baton:status`. |
| Гейт, который всегда пропускает | Тест 2 в CI. Асимметрия полномочий. `verify_cmd` живёт в файле, который агент не пишет. |
| Дрейф формата артефактов | `schema:` в frontmatter с первого дня. |
| Хрупкость хуков | Файлы авторитетны, хуки вспомогательны, скилы дублируют. Тест 4. |
| Тихая рассинхронизация состояния и репозитория | Заявленные поля никогда не чинятся молча — только `suspect` и вопль. |
| Ослабленный критерий: спека волны написана агентом и не ревьюится человеком | Суждение гейта якорится на `exit_criteria` конституции; спека волны может добавлять, но не ослаблять. |
| Goal drift: текущий запрос выполнен, правило из брифа нарушено | `Non-negotiables` восстанавливаются вместе с целью при каждом подъёме. |
| Переделывание уже реализованного на свежем контексте | Совещательное правило в `baton-resume` и Red Flags. |

## 14. Что не входит в v1

Отвергнуто, с причиной — чтобы через месяц это читалось как решение, а не как недосмотр.

- **Синхронизация с внешними трекерами** (Linear и подобные) — плагин публичный, чужого стека не предполагаем.
- **Шардирование состояния** под независимые параллельные сессии — отвергается замком.
- **Сверка на каждом вызове инструмента.** Уточнение, чтобы это не читалось как отказ от level-triggered подхода: подход мы приняли целиком — агент нигде не полагается на «я помню, что сделал X», он пересверяет заявленное с наблюдаемым в репозитории. Отложен только период сверки: он равен чекпойнту и гейту, а не каждому шагу. Пропущенное между сверками ловится следующей сверкой — ровно то свойство, ради которого level-triggered и берут.
- **Откат коммитов волны** при провале гейта — выбрасывает часы работы из-за одной заглушки.
- **Скил декомпозиции** отдельно от `/baton:init` — декомпозиция живёт внутри `init`.
- **Отдельный артефакт Handoff.** В брифинге артефактов четыре; у нас три. Handoff нужен был как неизменяемый снимок в консистентной точке, но `state.md` коммитится, и `git log -p` даёт историю снимков надёжнее собственной реализации. Теряем возможность снять чекпойнт, не коммитя его, — а несохранённый чекпойнт всё равно не пережил бы падение.
- **API-фичи Anthropic** (context editing, memory tool, серверная компакция) при заявленных +39% и экономии 84% токенов — это параметры Messages API, а плагин Claude Code до них не дотягивается. Не «не нужно», а «не наш слой».
- **Чекпойнты и `/rewind` Claude Code** — не пересекаются с нами: это undo для кода, а не состояние задачи. Дополняют, не заменяют.
- **Поле `confidence`** в записи журнала (есть в рекомендованной схеме) — самооценка уверенности модели плохо калибрована, а решения о вмешательстве принимаются по `reversibility` и `blast_radius`, которые проверяемы.
- **Подписанные аттестации** в духе SLSA/in-toto — git-тег на закрытой волне даёт нужные 80% бесплатно.

## 15. Оговорки к источникам

- Перенос детерминированного replay из Temporal на LLM буквально невозможен: LLM недетерминированы. «Восстановление» здесь означает подъём состояния из файла плюс сверку с репозиторием, а не побитовое воспроизведение.
- Числа про reward hacking (63% на SWE-bench Pro, подверженность 50–70%) — из конкретных исследований на конкретных бенчмарках. Класс отказа реален, буквальная экстраполяция на этот сетап — нет.
- Утверждение входного отчёта про `.superpowers/sdd/` в Superpowers 5.1.0 не подтвердилось при проверке установленной версии.
