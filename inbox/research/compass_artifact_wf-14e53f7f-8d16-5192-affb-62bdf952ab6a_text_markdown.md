# Компилируемость: репозиторий знаний как объект сборки и проверки

## TL;DR
- Для репозитория знаний под LLM-агента формализация окупается ровно там, где она превращается в **исполняемую проверку с машиночитаемым выводом**: ссылочная целостность (lychee), валидация frontmatter по JSON Schema (check-jsonschema / remark-lint-frontmatter-schema), детерминированная генерация индексов с проверкой пустого diff. Всё это — недорогие high-ROI проверки, не требующие тяжёлой инфраструктуры.
- Тяжёлые инструменты (OPA/Rego/Conftest, Great Expectations, полноценные data-contract-фреймворки) на масштабе одного репозитория с одним владельцем — **overkill**: их следует заменять простым скриптом на Node/Python плюс JSON Schema, а границу проводить по числу независимых консьюмеров правил (один — скрипт, много — policy engine).
- Главный риск — **не недоформализация, а переформализация**: обязательные поля, которые некому заполнять, деградируют в мусор (Goodhart's law), а таксономии умирают. Свободная проза в `core/`, `knowledge/` и рассуждениях агента должна оставаться свободной; схематизировать следует только машинно-потребляемые метаданные и структурные инварианты.

## Key Findings

1. **Схема даёт fail-fast, а не порядок.** Astro Content Collections с Zod-схемами останавливают сборку при несоответствии frontmatter — «build fails loudly instead of deploying silently broken content». Это и есть основная ценность схемы: перевод класса ошибок «тихо сломанные метаданные» в «громкий отказ в CI».
2. **Ссылочная целостность — самая выгодная проверка.** lychee (Rust) сканирует 576 ссылок примерно за минуту в конкретном репозитории (analysis-tools-dev/static-analysis), даёт JSON-вывод и легко встаёт в CI. Для вики-ссылок Obsidian нужен кастомный резолвер.
3. **Fitness functions прямо переносятся на репозиторий.** Инварианты (сироты, глубина вложенности, запрещённые зависимости между разделами, обязательные поля по типу, свежесть индексов) выразимы как исполняемые проверки в духе ArchUnit/dependency-cruiser.
4. **Детерминированная генерация — ключ к «нулю ручной дисциплины».** Паттерн `generate && git diff --exit-code` (из go generate / Go-экосистемы) применим к оглавлениям, индексам README и агрегатам. Маркеры генерируемых блоков (cog, markdown-magic, doctoc) отделяют рукописное от машинного.
5. **Миграции неизбежны; спасает expand/contract + schema_version.** Полу-мигрированное состояние предотвращается инвариантом «нет документов старой версии» как отдельной проверкой и кодмодами через remark/unified AST либо gray-matter.
6. **Переформализация документирована как провал.** Metadata rot, tag soup, умирающие таксономии, ADR-инициативы, вырождающиеся в бюрократию к третьему-шестому месяцу, — всё это следствие обязательных полей без потребителя (Goodhart's law).

## Details

### 1. Схемы для документов: что реально ловит схема

**Astro Content Collections (Zod).** Каноничный пример «схема как контракт на этапе сборки». Из документации Astro: «Schemas enforce consistent frontmatter or entry data within a collection through Zod validation. A schema guarantees that this data exists in a predictable form when you need to reference or query it. If any file violates its collection schema, Astro will provide a helpful error.» Практический опыт (sourcier.uk): «Markdown is flexible to the point of being dangerous — nothing stops you from publishing a post with a missing title, a malformed date, or a cover image path that leads nowhere… Astro content collections solve this with Zod schema validation at build time. If the content doesn't match the schema, the build fails loudly instead of deploying silently broken content.» Практический совет из руководств: «Minimize required fields; use .optional() and .default() elsewhere to ease migrating older posts» и `z.coerce.date()` для дат — прямое смягчение проблемы миграций.

**Класс ошибок, который ловит схема:** отсутствующие обязательные поля, неверный тип (строка вместо даты), несогласованный регистр/enum тегов, битые ссылки на связанные записи (`reference()`), пути к несуществующим ассетам. Чего схема НЕ ловит: смысловую корректность, устаревание контента, дубли по смыслу.

**Валидаторы frontmatter вне SSG:**
- `remark-lint-frontmatter-schema` (JulianCataldo) — валидирует YAML frontmatter против JSON Schema как remark-lint-правило, с указанием позиции ошибки для подсветки в IDE, автофиксами-подсказками, CLI и VS Code. Вывод вида: `1:1 warning Must have required property 'tag' frontmatter-schema remark-lint`. Именно на этой библиотеке частично строит отчёты Astro Content. В README сам автор помечает часть функций как WIP и намеренно разделяет статический линтинг (в редакторе) и runtime-валидацию во фреймворках.
- `check-jsonschema` (репозиторий python-jsonschema) — «A JSON Schema CLI and pre-commit hook built on jsonschema»; валидирует JSON и YAML против JSON Schema. Инвокация: `check-jsonschema --schemafile ./foo-schema.json instance1.yaml instance2.yaml`. Тип файла определяется автоматически, есть `--force-filetype yaml`. Поддерживает кастомные валидатор-классы через `--validator-class module:Class`. Есть официальный pre-commit hook. Важное ограничение: **не парсит markdown и не извлекает frontmatter сам** — нужно предварительно вытащить frontmatter в отдельный YAML/JSON-поток.
- `yamale` (23andMe) — «A schema and validator for YAML»; схема пишется в YAML через валидаторы (`str()`, `int()`, `include()` для рекурсии), CLI `yamale [-s SCHEMA] [PATH]` обходит каталоги («Yamale will search the directory you supply… for YAML files»), strict-by-default с `--no-strict`, есть `YamaleTestCase` для CI.

**Obsidian как де-факто схема.** У Obsidian нет жёсткой схемы; её роль выполняют плагины:
- **Dataview** превращает vault в запрашиваемую БД поверх frontmatter и inline-полей (`key:: value`). Пустые Dataview-таблицы — де-факто сигнал нарушения «схемы».
- **Metadata Menu** — «made for data quality enthusiasts»: типизированные поля с пресетами через `fileClass` (по сути класс-определение: «The type of a note is the class that defines which properties the note should have»). Автокомплит по пресет-значениям снижает tag soup.
- **Obsidian Bases** (нативные `.base`-файлы) — табличные представления коллекций поверх свойств; ограничения представления работают как мягкая схема.
- Риск, документированный практиками: «You add a tag here, a status field there — and suddenly half your notes have inconsistent frontmatter, your Dataview queries keep returning empty tables.» То есть без внешней проверки Obsidian-«схема» не гарантирует ничего — она лишь удобство ввода.

### 2. Миграции схемы контента

**База — expand/contract (parallel change).** Классический паттерн БД-миграций (Prisma, PlanetScale, Pete Hodgson): три фазы. Expand — добавить новое поле, не трогая старое; Migrate — backfill + двойная запись; Contract — удалить старое, когда никто его не читает. Pete Hodgson: «first Expanding the system so that it supports both the old and the new schema, and only once all parts of the system support the new schema do we Contract by removing support for the old schema.» Для репозитория знаний с одним владельцем фаза «двойного чтения» короткая, но принцип «сначала совместимость, потом удаление» защищает агента от чтения полусломанных документов.

**Версионирование.** Поле `schema_version` в frontmatter (аналог версий Flyway/Alembic/Rails migrations). Инвариант «нет документов версии < N» выражается отдельной исполняемой проверкой — это и есть защита от полу-мигрированного состояния: CI падает, пока хоть один файл не мигрирован.

**Кодмоды для markdown.** Массовая правка через AST: remark/unified (`remark-frontmatter` парсит YAML в MDAST-узел, обход `visit`), либо скрипты на `gray-matter` (актуально поддерживается, широко принято в Jamstack). Тонкость, документированная в remark-сообществе: правка `file.data.matter` не отражается обратно в вывод без корректного стрингификатора — для перезаписи frontmatter надёжнее gray-matter round-trip. Аналогия с jscodeshift для JS прямая: парсим в дерево, трансформируем, сериализуем.

**Как избежать полу-мигрированного состояния:**
1. Миграция — атомарный коммит (кодмод по всему корпусу за раз), а не «по мере прикосновения».
2. Инвариант-проверка «все файлы на целевой версии» в CI.
3. Идемпотентный кодмод (повторный запуск — no-op), проверяемый через `git diff --exit-code`.

### 3. Fitness functions и архитектурные тесты

Определение (Ford/Parsons/Kua, «Building Evolutionary Architectures»): «any mechanism that performs an objective integrity assessment of some architecture characteristic.» Инструменты структурных инвариантов: ArchUnit (Java), dependency-cruiser (JS), ts-arch, import-linter (Python), deptrac (PHP). Thoughtworks Technology Radar держит architectural fitness function как технику.

**Прямой перенос на репозиторий знаний** (aipatternbook формулирует: «A fitness function enforces an architectural invariant: a structural condition that must always hold… Tests verify behavioral correctness; fitness functions verify structural correctness»). Выразимые как исполняемая проверка инварианты:
- **Ссылочная целостность** — все `[[wikilinks]]` и относительные ссылки резолвятся.
- **Сироты** — ноты без входящих ссылок вне разрешённых зон (`inbox/`, `sources/`).
- **Глубина вложенности** — папки не глубже N уровней.
- **Обязательные поля по типу** — нота типа `project` обязана иметь `status` и критерий завершённости.
- **Запрещённые зависимости между разделами** — например, `sources/` (неизменяемое сырьё) не должно ссылаться на `tmp/`; `core/` не должно зависеть от `projects/` (аналог правила «ui не импортирует db»).
- **Свежесть индексов** — README/индексы не старше содержимого папки (аналог dbt source freshness).

### 4. Policy-as-code: где граница

OPA/Rego + Conftest — стандарт для проверки структурированных конфигов (Conftest: «Write tests against structured configuration data using the Open Policy Agent Rego query language»). Модель: input(JSON) → policy(Rego) → decision. Conftest ищет правила `deny`/`violation`/`warn`.

**Вердикт для одного репозитория с одним владельцем: overkill.** Обоснование:
- Rego — отдельный декларативный язык с нетривиальной кривой обучения («Developers familiar with imperative programming may find it unintuitive at first»); это постоянная стоимость сопровождения ради выгод, которые на одном репозитории не реализуются.
- OPA окупается, когда одни и те же политики применяются к **множеству независимых консьюмеров** (десятки сервисов/кластеров, требование единого аудируемого свода). У репозитория знаний консьюмер один — агент + владелец.
- Практик прямо отмечает overkill-зоны OPA (производительность на больших JSON, кривая Rego, отсутствие нативного enforcement).

**Граница:** если правило одно-два и живёт в одном репозитории — простой скрипт на Node/Python + JSON Schema. Policy engine оправдан при (а) переиспользовании одного свода правил между многими репозиториями-контекстами (что как раз планируется — «таких репозиториев уже несколько, будет больше»), И (б) потребности в едином машиночитаемом отчёте о соответствии. Даже тогда дешевле начать с общей npm/pip-библиотеки проверок, чем с Rego.

### 5. Генерируемые артефакты и детерминизм

**Паттерн «generate + проверить пустой diff».** Из Go-экосистемы: `go generate ./... && git diff --exit-code`; обобщённо `make generate && git diff --exit-code`. Логика (alexwlchan): «run the autogen in CI, then check it didn't change anything — that all the autogenerated files are already checked in». Это переносит поддержание индексов/оглавлений с ручной дисциплины на CI: агент/рутина генерирует, CI падает, если результат разошёлся с закоммиченным.

**Инструменты генерации с маркерами:**
- **cog** (Ned Batchelder) — исполняет Python внутри файла между маркерами `[[[cog ... ]]] ... [[[end]]]`; маркеры прячутся в комментариях любого языка, файл коммитится целиком. Есть режим проверки.
- **markdown-magic** — `<!-- AUTO-GENERATED-CONTENT:START --> ... :END -->`, синхронизирует блоки из кода/remote/TOC.
- **embedme** — вставляет код-сниппеты в markdown; `--verify` для CI («check that there are no changes expected to your files»).
- **doctoc** — генерация TOC; CI-проверка через `--dryrun` (exit 1, если TOC устарел — «useful in CI environments where you want to check if your docs are up to date»), НЕ через флаг `--check`. Маркеры: `<!-- START doctoc ... -->` / `<!-- END doctoc ... -->` (compact: `<!-- START doctoc -->`). Есть pre-commit hook. Идемпотентен: повторный запуск обновляет существующий TOC, а не дублирует.
- **markdown-toc** — маркеры `<!-- toc -->` / `<!-- tocstop -->`, `-i` для правки на месте; встроенного check-режима нет — паттерн вручную: `markdown-toc -i FILE && git diff --exit-code`.

**Проблемы недетерминизма** (главный враг паттерна «пустой diff»): нестабильная сортировка, таймстемпы, порядок обхода файлов, различия отступов/переносов между локальной и CI-конфигурацией, конфликт с форматтерами (Prettier). doctoc добавил `--toc-title-padding-before` именно ради совместимости с Prettier. Практика: фиксировать флаги/renderer-режим, сортировать детерминированно (по имени файла), исключать таймстемпы из генерируемых блоков.

### 6. Модель dbt: тесты как часть определения модели

dbt даёт готовую ментальную модель «данные + тесты + документация + происхождение в одном определении»:
- **Тесты в schema.yml** — `unique`, `not_null`, `relationships` (referential integrity), объявляются рядом с моделью.
- **Source freshness** — `warn_after`/`error_after` по `loaded_at_field`; `dbt source freshness` падает, если данные устарели сверх SLA. Прямой аналог проверки свежести индексов/`state.md`.
- **Contracts** (доступны с dbt ≥1.5) — схема как контракт, проверяется до материализации; shift-left-подход «catches breaking changes in development rather than production, safeguarding downstream pipelines».
- **Lineage/происхождение** — граф зависимостей моделей.

**Что переносится на markdown-корпус:** идея, что проверки данных — часть определения (рядом с контентом лежит его контракт), разделение «контракт схемы» (до) и «тесты семантики» (после), freshness как первоклассная проверка, data contract как соглашение продюсер↔консьюмер (здесь: владелец-человек ↔ агент-консьюмер). Тяжёлые data-quality фреймворки (Great Expectations, Soda, Pandera, Deequ, Monte Carlo) для одного markdown-репозитория избыточны — берём паттерн, не инструмент.

### 7. Исполняемая документация

- **doctest (Python)** — «literate testing / executable documentation»; примеры в докстрингах исполняются и проверяются. Практик: «treat doctests as a documentation integrity layer» — держать в них маленькие детерминированные примеры, тяжёлую логику выносить в unit-тесты. Ограничение: недетерминированный вывод (id, время) ломает doctest.
- **xdoctest** — AST-парсер вместо regex, плагин к pytest (`pytest --xdoctest`).
- Rust doctests, Go Example functions, mdBook/rustdoc — тот же принцип «примеры в доках компилируются и запускаются в CI».
- **Specification by example / Cucumber / Concordion / FitNesse** — исполняемые спецификации.

**Применимость к репозиторию знаний:** блоки в `knowledge/`, содержащие команды/сниппеты/конфиги, можно помечать как исполняемые и проверять запуском (или через embedme — синхронизировать с реальным исходником). Это защищает от дрейфа «документация говорит одно, реальность другое».

### 8. Границы формализации: что НЕ формализовывать

Это критический раздел, и опыт документирован как серия провалов:

- **Metadata rot / tag soup.** Обязательные поля без потребителя заполняются мусором. Практики Obsidian: несогласованный frontmatter, пустые Dataview-таблицы. Совет PKM-сообщества — «Stupid Simple», «connect, not collect»; попытки загнать всё в одну систему «working at cross-purposes».
- **Goodhart's law.** «When a measure becomes a target, it ceases to be a good measure» — эту формулировку ввела антрополог Marilyn Strathern (1997), обобщив исходную формулу Charles Goodhart (1975: «Any observed statistical regularity will tend to collapse once pressure is placed upon it for control purposes»). Как только «полнота метаданных» становится целью, поля заполняются формально. Manheim & Garrabrant формализуют варианты (regressional и др.); это прямо релевантно метрикам качества документации и «governance-task decoupling» (surface adherence вместо содержательного соответствия).
- **Умирающие таксономии.** Жёсткие онтологии/таксономии в корпоративном KM регулярно вырождаются; folksonomy живее, но менее точна.
- **ADR как индикатор.** Где сработало: короткие ADR с явными trade-offs. Где выродилось (HelixGate, документированный failure mode): «By month three, the space has 40 pages, no consistent structure, and the search is useless. By month six, people have stopped writing new ones because nobody reads them anyway.» Симптом переформализации: «Nobody wants to write ADRs because they feel like bureaucracy.» Правило: «Keep ADRs small and fast to write — aim for a page, not a report.»

**Явный список того, что оставлять свободной прозой** (для гипотезы структуры заказчика):
- `core/` — принципы, правила принятия решений: свободная проза + минимум машинных полей (`id`, `type`). Смысл принципа не схематизируется.
- `knowledge/` тело нот — проза; схематизировать только frontmatter-обёртку (тип, теги из контролируемого словаря, ссылки на источники).
- Автогенерируемый журнал размышлений агента — не схематизировать содержание, только метаданные записи (timestamp, session-id).
- `inbox/` — намеренно бесструктурная зона захвата; жёсткая схема здесь убивает функцию «единой точки входа».
- Лог решений (decision log) — держать ADR-lite: 1 экран, обязательны только context/decision/consequences, остальное — проза.

**Критерий «что формализовать»:** формализуй поле ⟺ у него есть **машинный потребитель** (агент запрашивает, рутина сортирует, проверка валидирует). Поле, которое читает только человек в прозе, — оставить прозой.

### 9. Обратная связь для автоматики (критично для LLM-агента)

Репозиторий обслуживает агент, поэтому вывод проверок должен быть **машиночитаемым и самодостаточным для исправления**.

- **Эталон дизайна ошибок — Elm/Rust.** Evan Czaplicki, создатель Elm, в «Compiler Errors for Humans» (elm-lang.org, 2015) сформулировал подход: показывать точный фрагмент кода, номера строк, «jump to error». Rust перенял подход; rustc-гайд: сообщение должно указывать span, быть кратким, с расширением по `--explain`, не дублироваться, предлагать fix. Для линтеров репозитория это означает: сообщение = {что нарушено, где (файл:строка), как починить}.
- **Машиночитаемый вывод.** lychee, markdownlint и др. дают JSON; SARIF — стандарт для агрегации. Для агента предпочтителен структурированный вывод (JSON/SARIF), который он парсит и по которому строит правку — это и есть цикл самокоррекции («detect-then-rewrite», «the agent parses the error log and generates a correction commit»).
- **Автофиксы (`--fix`).** Где возможно (prettier/mdformat для форматирования, remark-автофиксы, markdownlint `--fix`) — автоправка снимает нагрузку и с человека, и с агента.
- **Guardrails-конвенции.** CLAUDE.md/AGENTS.md как навигационный корень + per-folder инструкции; проверки работают как guardrails. Документированная практика: «Every comment a reviewer leaves on an AI-assisted PR is a signal that the agent lacked context» → правило добавляется в CLAUDE.md/чеклист. Слоистая защита: детерминированные pre-LLM проверки → policy-enforced исполнение → post-LLM валидация с self-correction петлёй. Важно: файл-правила (CLAUDE.md) недетерминированны как enforcement — «The AI may ignore, forget, or misinterpret rules»; поэтому жёсткие инварианты должны быть исполняемыми проверками, а не строчками в инструкции.

## Каталог проверок (ранжирован по польза/стоимость для сотен-тысяч файлов, один владелец)

Формат: **что проверяет | класс ошибок | внедрение | сопровождение | ложноположительные | нужна ли схема | инструмент**.

**Ранг 1 — Ссылочная целостность (внутренняя).**
Все относительные/`[[wiki]]`-ссылки и пути к ассетам резолвятся | битые ссылки, переименования, удалённые файлы | низкое | низкое | внешние URL могут флапать (503/429), приватные ссылки; вики-ссылки Obsidian требуют кастомного резолвера | нет | lychee (внутренние), кастомный скрипт для `[[wiki]]`.

**Ранг 2 — Детерминированная генерация индексов/TOC с проверкой пустого diff.**
README-индексы, оглавления, агрегаты актуальны | рассинхрон индекса и содержимого, ручной дрейф | низкое-среднее | низкое | недетерминизм (сортировка/таймстемпы/форматтер) даёт ложный fail | нет | doctoc `--dryrun` / markdown-magic / cog + `git diff --exit-code`.

**Ранг 3 — Валидация frontmatter по JSON Schema.**
Обязательные поля по типу, типы значений, enum тегов | отсутствующие/битые метаданные, tag soup | среднее (написать схемы) | низкое-среднее (эволюция схем) | слишком строгая схема бьёт по легаси-файлам; лечится `.optional()`/`.default()` | да | check-jsonschema / remark-lint-frontmatter-schema / Zod (если SSG).

**Ранг 4 — Структурные fitness functions.**
Сироты, глубина вложенности, запрещённые зависимости между разделами, обязательные поля по типу | эрозия структуры, недопустимые связи | среднее | низкое | легитимные исключения (намеренные сироты в `inbox/`) → нужны allowlist-зоны | частично (типы нот) | кастомный скрипт (Node/Python) в духе dependency-cruiser.

**Ранг 5 — Свежесть индексов/состояния.**
Индекс/`state.md` не старше содержимого папки | устаревшие индексы, забытый backfill | низкое | низкое | легитимно замороженные архивы дают ложный сигнал → исключать `archive/` | нет | скрипт сравнения mtime/git-времени (аналог dbt freshness).

**Ранг 6 — Инвариант версии схемы (анти-полу-миграция).**
Нет документов версии < целевой | застрявшая миграция | низкое | низкое (растёт при частых миграциях) | почти нет | да (`schema_version`) | скрипт-проверка + кодмод remark/gray-matter.

**Ранг 7 — Формат/линт markdown.**
Единый стиль, валидный markdown | сломанный синтаксис, шумные диффы | низкое | низкое | стилевые правила субъективны; держать минимальный набор | нет | markdownlint (`--fix`), prettier/mdformat.

**Ранг 8 — Исполняемые блоки (doctest-стиль).**
Команды/сниппеты в `knowledge/` реально работают/синхронны | дрейф «доки vs реальность» | среднее-высокое | среднее | недетерминированный вывод ломает проверку | нет | embedme `--verify` / doctest-подобные раннеры.

**Ранг 9 (обычно НЕ рекомендуется) — Prose linting (Vale).**
Стиль/терминология прозы | несогласованный стиль | среднее | среднее-высокое | много ложных срабатываний на живой прозе; окупается от ~20 страниц и многих авторов | нет | Vale. Для одного владельца — избыточно; включать точечно (контролируемый словарь терминов).

**Ранг 10 (НЕ рекомендуется на одном репозитории) — Policy-as-code (OPA/Rego/Conftest).**
Сложные политики над структурой | нарушения политик | высокое (Rego) | высокое | зависит от политик | да (input как JSON) | Conftest. Оправдан только при переиспользовании свода правил между многими репозиториями-контекстами.

## Рекомендуемая стратегия миграций схемы (пошагово)

1. **Введи `schema_version` в frontmatter** каждого типизированного документа с самого начала. Без версии миграции неуправляемы.
2. **Проверка-инвариант в CI: «нет документов версии < текущей».** Это единственная надёжная защита от полу-мигрированного состояния — CI красный, пока корпус не мигрирован целиком.
3. **Expand.** Добавь новое поле/структуру, не удаляя старое. Схема временно допускает оба варианта (`.optional()` на новом поле).
4. **Backfill кодмодом.** Идемпотентный скрипт (remark/unified AST для тела, gray-matter для round-trip frontmatter) проставляет новое поле по всему корпусу одним атомарным коммитом. Идемпотентность проверяй `git diff --exit-code` при повторном запуске.
5. **Переключи консьюмеров** (агент, Dataview-запросы, генераторы) на новое поле. При необходимости короткая фаза двойного чтения.
6. **Contract.** Удали старое поле кодмодом; ужесточи схему (новое поле → `required`); подними целевую `schema_version`. Инвариант из шага 2 гарантирует отсутствие остатков.
7. **Автоматизируй как рутину обслуживания.** Миграция — это скрипт в репозитории, а не ручная операция; агент/CI могут запускать её и отчитываться машиночитаемо.

Паттерн заимствован из БД-миграций (expand/contract = parallel change, Flyway/Alembic/Rails как аналог версионирования) и адаптирован под один корпус: фазы совместимости короткие, но порядок «совместимость → backfill → удаление» сохраняется.

## Что формализовывать НЕ следует (явный список)

1. **Смысловое тело `core/` и `knowledge/`** — принципы, рассуждения, экспертиза. Схематизируй только обёртку-frontmatter. Обоснование: попытки схематизировать смысл ведут к потере смысла (умирающие таксономии, критика жёстких онтологий в KM).
2. **Содержание `inbox/`** — намеренно бесструктурная точка захвата. Жёсткая схема убивает функцию. Разбор — потом, при переносе в целевую папку.
3. **Автогенерируемый журнал размышлений агента** — схематизируй только метаданные записи (timestamp, session-id), не содержание.
4. **Обязательные поля без машинного потребителя** — прямой путь к metadata rot и Goodhart-мусору. Критерий: поле формализуется ⟺ его читает машина (агент/рутина/проверка).
5. **Развесистые ADR** — держать ADR-lite (1 экран). Документированный провал: формальные тяжёлые ADR перестают писать и читать к 3–6 месяцу.
6. **Prose style на масштабе одного владельца** — Vale окупается от ~20 страниц и нескольких авторов; для одного человека это налог без выгоды.
7. **Жёсткие иерархические таксономии тегов** — предпочесть контролируемый плоский словарь (enum в схеме) + автокомплит (Metadata Menu), а не глубокую онтологию.

## Recommendations

**Этап 0 (день 1, обязательный минимум).** Внедри три high-ROI проверки: (1) внутренняя ссылочная целостность (lychee + кастомный резолвер `[[wiki]]`); (2) детерминированная генерация индексов README/TOC с `git diff --exit-code`; (3) markdownlint + prettier/mdformat с `--fix`. Все три — низкая стоимость, немедленная отдача, машиночитаемый вывод для агента.

**Этап 1 (неделя 1).** Введи `schema_version` и JSON Schema для типизированных документов (`project`, `area`, source-нота). Валидатор — check-jsonschema (с предварительным извлечением frontmatter) или remark-lint-frontmatter-schema. Минимизируй `required`-поля; расширяй схему по мере появления реальных машинных потребителей.

**Этап 2 (неделя 2–3).** Напиши структурные fitness functions одним скриптом (Node/Python): сироты (с allowlist для `inbox/`/`sources/`), глубина вложенности, запрещённые зависимости между разделами, свежесть индексов. Вывод — JSON, чтобы агент сам исправлял.

**Этап 3 (по мере роста числа репозиториев).** Вынеси проверки в общую библиотеку (npm/pip), переиспользуемую всеми репозиториями-контекстами. Только если появится потребность в едином аудируемом своде правил между многими репозиториями — рассмотри Conftest/OPA; до этого держись скрипта.

**Пороги пересмотра решений:**
- Переходить на policy engine (OPA) — когда один свод правил обслуживает **≥3–5 репозиториев** И нужен единый машиночитаемый отчёт о соответствии.
- Включать Vale — когда авторов **>1** или объём прозы, требующей единого стиля, превышает ~20 страниц.
- Усложнять схему — только когда у нового поля появился реальный машинный консьюмер; иначе оставить прозой.
- Если поле систематически заполняется мусором или пустым — это сигнал Goodhart: убрать из `required` либо удалить.

## Caveats

- Часть источников по инструментам — вендорские/блоговые (astrocourse, sourcier, docsio, buildwithfern); фактура о поведении инструментов перепроверяется по официальной документации (Astro Docs, conftest.dev, lychee.cli.rs, dbt docs, nedbatchelder.com), но конкретный тайминг lychee («576 ссылок за ~1 минуту» для analysis-tools-dev/static-analysis) относится к конкретному репозиторию и не является универсальным бенчмарком.
- `remark-lint-frontmatter-schema` в собственном README помечает часть функций как WIP; runtime-валидация внутри фреймворков и статический линтинг — разные сценарии, их автор намеренно разделяет.
- Утверждение о недетерминизме doctoc/markdown-toc не подтверждено как баг в официальных README; документирована лишь чувствительность к флагам/renderer-режиму и совместимости с форматтерами — трактовать как «стабильность вывода зависит от единых флагов», а не как дефект.
- Тезисы о провалах формализации (metadata rot, вырождение ADR, Goodhart) опираются на широко воспроизводимый практический опыт сообществ и литературу, но это качественные наблюдения, а не контролируемые измерения; масштаб эффекта зависит от дисциплины конкретного владельца.
- Специфика «репозиторий обслуживает LLM-агент» — молодая область; конвенции AGENTS.md/CLAUDE.md и guardrails эволюционируют, устойчивых долгосрочных бенчмарков пока нет.
