# Жизненный цикл документа: протухание, устаревание, удаление (R3)

## TL;DR
- Ручная дисциплина не масштабируется: единственный надёжный механизм борьбы с протуханием — машинно-проверяемые метаданные свежести (`owner` + `reviewed`/`valid_until` во frontmatter) плюс CI-проверка, которая заводит задачу/падает при просрочке; всё остальное деградирует. Подтверждено практикой Google («freshness dates» с email-напоминаниями при отсутствии правок ~3 месяца) и эмпирикой (Aghajani et al., ICSE 2019: устаревание — одна из трёх базовых категорий проблем содержания документации из таксономии в 162 типа).
- Разным классам контента нужен разный режим жизненного цикла: evergreen и ADR/RFC — append-only с явным статусом (`superseded`, а не удаление); knowledge — demand-driven ревью (KCS «reuse is review»); source — иммутабельный write-once; tmp — TTL с автоудалением. Тип документа должен быть машиночитаемым полем `type`, а не негласным соглашением.
- Директория `archive/` при наличии git в большинстве случаев ИЗБЫТОЧНА как «склад старого», но ОПРАВДАНА в одном сценарии: когда исторический документ должен оставаться человеко/агенто-читаемым, но обязан быть исключён из активного контекста и поиска. Ключевой риск архива — не потеря, а обратное: кто-то (или агент) находит и применяет устаревшее как действующее.

## Key Findings

1. **Устаревание измеримо и составляет крупную долю проблем документации.** Эмпирическое исследование Aghajani et al. («Software Documentation Issues Unveiled», ICSE 2019, DOI 10.1109/ICSE.2019.00122) намайнило и категоризировало 878 связанных с документацией артефактов из четырёх источников и построило таксономию из 162 типов проблем, где Up-to-dateness (актуальность) — одна из трёх категорий содержания наряду с Correctness и Completeness (последующий опрос практиков — 146 участников). Tan, Wagner & Treude (Empirical Software Engineering 29:5, 2024, DOI 10.1007/s10664-023-10397-6) на >3000 GitHub-проектов установили дословно: «28.9% of the most popular projects on GitHub currently contain at least one outdated reference, with 82.3% of the projects being outdated at least once during the project's history. These references were typically outdated for years before they were noticed and fixed». Wen et al. (ICPC 2019; 1.3 млрд изменений, 1500 систем): «в большинстве случаев код и комментарии не эволюционируют совместно».

2. **Google как эталон машинной проверки свежести.** В «Software Engineering at Google» (Winters, Manshreck, Wright, гл. 10) описан механизм freshness dates дословно: «we often attach 'freshness dates' to documentation… metadata in the documentation set will send email reminders when the document hasn't been touched in, for example, three months». Документ несёт frontmatter-блок `owner:` и `reviewed: '2019-02-27'`; включение владельца с байлайном «Last reviewed by…» повысило adoption. При хранении под контролем версий обновление даты требует code review — это дешёвый способ гарантировать периодический осмотр.

3. **KCS: актуальность через спрос, а не плановые ревью.** Consortium for Service Innovation (KCS v6 Practices Guide, Technique 5.2) формулирует принцип «reuse is review» — статья улучшается при каждом переиспользовании. Плановое ревью без спроса — прямой анти-паттерн, дословно: «Do not review articles for the sake of review, as they may never be reused. If we are reviewing articles in absence of demand, we are not doing KCS». Потерявшая актуальность статья не удаляется физически (это ломает связи с инцидентами), а переводится в состояние Archived: «remove the article from the searchable knowledge base without physically deleting it. An archived article can be restored to any other confidence setting». KCS различает три оси состояния: confidence, audience (visibility), governance.

4. **ADR/RFC: append-only и статус вместо удаления.** Консенсус (Nygard, MADR, Backstage, IETF): решения никогда не удаляются. Меняется только поле Status: Proposed → Accepted → Deprecated/Superseded. Superseded-ADR получает ссылку на заменяющий, новый — обратную ссылку. Тело после принятия иммутабельно; изменения фиксируются в Errata (RFC-практика Apache Geode). IETF использует статус «Historic» для устаревших/замещённых спецификаций (RFC 2026 §4.2.4). MADR 4.0.0 хранит метаданные в YAML frontmatter; есть YAML-ADR (YADR) и structured-MADR (risk assessment + audit trail, JSON-LD, GitHub Action-валидатор) для машинной обработки. Причина сохранения: отклонённые/замещённые решения не дают повторно передоговариваться об уже оценённых вариантах.

5. **Удаление против архивирования.** ISO 15489 требует retention/disposition schedule: срок хранения по правовой/бизнес-ценности/риску, disposition action (review / transfer to archive / export / destruction), авторизованное уничтожение, audit trail, возможность hold (заморозка удаления). Архив как «место, куда сложили и забыли» — источник вреда: устаревший runbook, найденный во время инцидента, увеличивает MTTR (в одном описанном практическом случае on-call инженер потратил 45 минут по устаревшему runbook — SSH на выведенный из эксплуатации сервер — при отладке с нуля за 20 минут; заявленная потеря ~$120k выручки). Практики безопасного архива: deprecation-баннеры (Kubernetes, Read the Docs, Rust docs), редиректы на актуальную версию, `noindex`/robots.txt для исключения из поиска.

6. **Типизация документов (Diátaxis) даёт выигрыш в поддержании актуальности.** Diátaxis (Daniele Procida): tutorial / how-to / reference / explanation по осям action↔knowledge и study↔work. Принят Django, Canonical, Cloudflare, Gatsby. Разные типы имеют принципиально разный срок жизни: reference и how-to протухают вместе с продуктом (высокая частота ревью), explanation/принципы — evergreen. Главная ошибка — смешение типов на одной странице, что затрудняет и поддержку, и RAG. Чистый reference снижает галлюцинации в RAG, агент грузит только нужный квадрант, экономя контекст.

7. **Разделение источника и вывода.** GitLab: SSoT (single source of truth), «docs-first», организация по теме, а не по типу медиа; вместо дублирования — ссылка на канонический источник или генерация/встраивание («Create Once, Publish Everywhere»). Практика data lineage/provenance: иммутабельные снапшоты сырых данных, идентификаторы источников (source URN), прослеживаемость производного до источника, обратный lineage (от плохого источника найти все затронутые выводы). Для repo-контекста агента это означает: `sources/` иммутабельны, производные документы несут поле `provenance`/`source` со ссылкой на исходник.

8. **Передача правки автоматике: риск тихой деградации.** LLM-генерация документации «звучит правильно, но неверна» (Scott McMaster о AWS DataZone). Академическая работа по README-maintenance (arXiv) показывает: полная регенерация файла деструктивна — style drift, галлюцинации, «Lost in the Middle», высокая нагрузка на ревью; правильнее «хирургические» точечные правки. Silent degradation: система выдаёт синтаксически валидные, но всё менее точные ответы без явных сбоев; «green dashboards» не означают корректность. Требования: human-in-the-loop review перед публикацией, регрессионные проверки, diff-ревью малых изменений вместо переписывания целиком.

## Details

### Doc rot: измеримость, стоимость, механизмы выявления

Количественная база (приоритет — рецензируемые источники):
- **Prevalence.** Aghajani et al., ICSE 2019: таксономия из 162 типов проблем, где актуальность (up-to-dateness) — одна из трёх категорий содержания. Tan/Wagner/Treude, EMSE 2024: 28.9% топ-проектов GitHub содержат устаревшие ссылки на код, 82.3% — были устаревшими хотя бы раз, «устаревали годами». Wen et al., ICPC 2019 (1.3 млрд изменений, 1500 систем): «в большинстве случаев код и комментарии не эволюционируют совместно».
- **Стоимость.** Прямых рецензируемых цифр «стоимости решений на устаревшем документе» нет. Индустриальные оценки: Stripe & Harris Poll «The Developer Coefficient» (2018; опрос >1000 разработчиков и >1000 C-level в US, UK, France, Germany, Singapore) — дословно «the average developer spends more than 17 hours a week dealing with maintenance issues… they spend approximately four hours a week on 'bad code,' which equates to nearly $85 billion worldwide in opportunity cost lost annually». Это оценка техдолга в целом, НЕ документации в частности. Stack Overflow (2024): >30 минут/день на поиск решений, включая «hunting down missing documentation». Postman State of the API: недостаток/несогласованность документации — препятствие №1 для потребления API, ~52–55% ежегодно.

Механизмы выявления протухшего (по возрастанию машинной проверяемости):
- **Метаданные свежести + owner** (Google): `owner`, `reviewed` во frontmatter; CI/бот шлёт напоминание при просрочке. Failure mode: владелец обновляет дату не читая («date swap») — свежесть формально есть, фактически нет. Митигация: связывать дату с реальным diff.
- **TTL / valid_until.** Явная дата протухания. Confluence CLM (Midori «Better Content Archiving», политика Sentry): уведомления заранее (~150 дней), затем авто-архив при отсутствии реакции. Разные типы контента — разные окна (месячный отчёт — 30 дней; product-manual — 500 дней без просмотров → отчёт лидеру).
- **Обязательный owner.** Confluence-аудиты (Stale Page Finder, gocapable «Capable Quality» как «линтер контента»): корневая причина rot — отсутствие явного владельца на пространство. «Trust cliff»: как только читатели перестают доверять wiki, они уходят в Slack, и вся написанная документация обесценивается.
- **Линтеры docs-as-code.** Vale (используют Google, Microsoft, GitHub, RedHat, GitLab, Mozilla; Datadog — 14 писателей на 35 продуктовых областей); проверки терминологии, запрещённых слов, стиля; в CI блокирует PR. Failure mode: false positives на code-shortcodes; регуляция уровней (Priority/Warning/Info/Off).
- **Периодические ревью** работают ТОЛЬКО если машинно инициируются (задача/PR), иначе деградируют («heroic quarterly clean-up работает три недели, потому что ручной аудит — снимок, а контент — поток»).

### KCS и курирование при массовом создании
- Контент создаётся как побочный продукт решения проблемы; эволюционирует по спросу и использованию.
- «Reuse is review»: правит тот, кто переиспользует, в момент переиспользования.
- Состояния: confidence (готовность/качество), audience/visibility, governance. Жизненный цикл нелинейный.
- Потеря актуальности → Archived (логическое удаление из поиска, восстановимо, не рвёт связи с тикетами).
- Анти-паттерн: ревью в отсутствие спроса.
- Применимость к repo агента: `knowledge/` курируется по обращениям агента; частота обращений = сигнал ценности; редко-читаемое — кандидат на архив, а не на плановое ревью.

### ADR/RFC: поля и накопление
Реально используемые поля (MADR 4.0.0 / Nygard / Backstage / structured-MADR):
- `title`, `status` (Proposed/Accepted/Rejected/Deprecated/Superseded), `date`, `deciders`, ссылки (`superseded_by` / `supersedes`), Context, Decision, Consequences, Options с pros/cons.
- YAML frontmatter для метаданных; structured-MADR добавляет risk assessment и audit trail, JSON-LD, GitHub Action-валидатор — позиционируется как «ADR для эпохи AI-разработки».
- Накопление сотен ADR: последовательная нумерация (ADR-0001…), хранение в `docs/adr|decisions/`, индекс/TOC, статус-фильтр для отделения действующих от исторических. Читатель отличает действующее по полю Status + баннеру superseded в теле.
- RFC (Uber/Pragmatic Engineer): при масштабировании главная проблема — шум (сотни RFC в неделю), решается сегментацией списков и tiered-процессом (формальное ревью только для критичных изменений). Статусная таблица (status, date) даёт полную историю.

### Удаление против архивирования
- ISO 15489: retention schedule = срок хранения (правовой/бизнес/риск), disposition action (review / transfer to archive / export / destruction), authorized disposal, audit trail, возможность hold.
- Архив как вред: устаревший найденный документ применяется как действующий (runbook-инцидент, +45 мин, ~$120k). Rust docs, Kubernetes, Read the Docs: обязательный deprecation-баннер + noindex + редирект на актуальную версию.
- Безопасное удаление при полной истории версий: git хранит содержимое навсегда; удаление из рабочего дерева = вывод из активного контекста без потери. Восстановление — `git log --diff-filter=D`/`git show`. При git «удаление» физически необратимой потерей не является, что снимает главный аргумент за `archive/`.

### Разделение источника и вывода
- SSoT (GitLab): один канонический документ на факт; вместо копий — ссылка/генерация. Организация по теме, не по типу.
- Provenance: иммутабельные сырые источники, идентификатор источника, прослеживаемость производного → источник, обратный lineage. Для агента: производный документ несёт `source:`/`provenance:` со ссылкой на `sources/<id>`; при изменении источника — найти затронутые выводы.

### Автоматика правит документацию
- Silent degradation: валидные, но всё менее точные ответы; «green dashboards» не означают корректность.
- LLM-регенерация деструктивна (style drift, галлюцинации); правильнее diff-правки.
- Требования: human-in-the-loop перед публикацией; регрессионные проверки; малые ревьюируемые diff; ограничение зон авто-записи (агент пишет в `tmp/`, `inbox/`, журнал; `core/` и `decisions/` — только через PR-ревью).

## Recommendations

### Набор правил жизненного цикла по классам контента (готов к переносу в конфигурацию)

**core/ (evergreen-принципы)**
- Режим записи: правки только через явный review (PR); высокий порог изменения.
- Признаки устаревания: противоречие с решениями в `decisions/`; расхождение с реальностью субъекта.
- Проверка: frontmatter `reviewed`, `owner`; CI-напоминание при `reviewed` старше 180–365 дней (evergreen — длинное окно).
- Вывод из обращения: не удаляется; переписывается in-place, история в git.
- Failure mode: «date swap» без чтения → привязать к diff; редкие правки маскируют дрейф → большое окно + перекрёстная проверка ссылками.

**decisions/ (ADR/RFC)**
- Режим: append-only; тело иммутабельно после Accepted; меняется только Status + Errata.
- Признаки устаревания: изменился контекст → нужен новый ADR, старый Superseded.
- Проверка: обязательные `status`, `date`, `id`; при Superseded — обязательное `superseded_by`; CI-валидатор (structured-MADR-подобный) на схему frontmatter и целостность ссылок.
- Вывод: никогда не удаляется; Status=Deprecated/Superseded + баннер в теле.
- Failure mode: сотни ADR → индекс + статус-фильтр; «тихая» правка тела → CI-запрет изменения тела при status=Accepted (хеш/protected-путь).

**projects/ (проектный документ)**
- Режим: активные правки; критерий завершённости во frontmatter.
- Признаки устаревания: проект завершён/заброшен (нет активности N дней).
- Проверка: `status: active|done|abandoned`, `due`/`completed`; CI помечает stale при отсутствии коммитов.
- Вывод: завершённый → перенос в `archive/` ИЛИ пометка `status: done` + исключение из активного индекса README; сырьё решений — в `decisions/`.
- Failure mode: заброшенные проекты копятся как активные → авто-флаг по mtime/commit-age.

**knowledge/ (доменная база)**
- Режим: демандо-ориентированные правки (KCS reuse-is-review); правит тот, кто использовал.
- Признаки устаревания: редко читается агентом + расхождение при использовании.
- Проверка: `owner`, `reviewed`; счётчик обращений агента как сигнал; НЕ плановое ревью.
- Вывод: потерявшее спрос → Archived (исключить из индекса/поиска, оставить восстановимым).
- Failure mode: плановые ревью без спроса (анти-KCS) → заменить на demand-триггер; «trust cliff» при накоплении неверного → быстрый flag «This no longer works».

**sources/ (сырьё)**
- Режим: иммутабельно, append-only (write-once).
- Признаки устаревания: неприменимо — источник не протухает, протухает его интерпретация.
- Проверка: CI-запрет на модификацию существующих файлов (только добавление); контрольная сумма/`captured_at`, `source_id`.
- Вывод: не удаляется и не правится; при необходимости — retention по ISO-подобному расписанию (напр., GDPR-обусловленное удаление ПДн) с audit trail.
- Failure mode: сырьё путают с выводом → строгая директория + frontmatter `type: source`; раздувание → retention-schedule только для регулируемых данных.

**tmp/ (временные артефакты)**
- Режим: свободная запись агентом в течение сессии.
- Признаки устаревания: истёк TTL / завершилась сессия.
- Проверка: `expires:`/`ttl`; авто-рутина удаляет просроченное; бот чистит по расписанию.
- Вывод: авто-удаление (git хранит историю, если было закоммичено); ценное — промотируется в `knowledge/` или `inbox/`.
- Failure mode: ценное теряется при чистке → правило «promote before expire»; `tmp` растёт бесконечно → жёсткий TTL по умолчанию.

### Единый frontmatter-контракт (машинно-проверяемый)
Минимальный набор полей, покрывающий все классы: `type` (evergreen|decision|project|knowledge|source|tmp), `owner`, `status`, `reviewed`, один из `valid_until`/`ttl`/`expires` (по классу), `provenance`/`source` (для производных), `superseded_by`/`supersedes` (для decisions). CI-валидатор схемы — единственная точка enforcement.

### Поэтапное внедрение
1. Ввести обязательный frontmatter-контракт и CI-валидатор схемы. Порог смены решения: если >20% файлов не проходят схему — сначала миграция, потом enforcement.
2. Включить freshness-бота (напоминание/задача при просрочке `reviewed` по классам с разными окнами).
3. Добавить Vale-подобный линтер прозы + проверку битых wiki-ссылок и целостности `superseded_by`.
4. Ограничить зоны авто-записи агента (tmp/inbox/журнал — свободно; core/decisions — только PR).
5. Настроить demand-сигнал для `knowledge/` (лог обращений агента) вместо плановых ревью.

Бенчмарк отказа от `archive/`: если за N месяцев ни один архивный документ не был запрошен человеком/агентом — `archive/` не нужен, git достаточно. Если запрашивается, но вредит — нужен не `archive/`, а deprecation-баннер + исключение из индекса.

## Нужна ли директория archive/ при наличии git

**Тезис: в большинстве случаев `archive/` избыточна; git закрывает функцию «не потерять». Но есть один класс задач, где `archive/` оправдана — когда документ должен оставаться человеко/агенто-читаемым, но обязан быть выведен из активного контекста.**

**Аргументы ПРОТИВ archive/:**
- git — уже полная неудаляемая история. Удаление файла из рабочего дерева не теряет содержимое (`git log --diff-filter=D`, `git show`). Главный аргумент за архив («вдруг понадобится») закрыт.
- Активный контекст агента — узкое место (context window). `archive/` в дереве = агент индексирует и потенциально читает устаревшее. Это прямой источник вреда (применение superseded как действующего).
- Дублирование механизма: две системы «истории» (git + `archive/`) размывают ответственность.

**Аргументы ЗА archive/:**
- git-история невидима для Obsidian-интерфейса человека и для агента, читающего рабочее дерево. Если исторический документ нужно читать без git-инструментов (человек листает в Obsidian, агент цитирует прецедент), `archive/` даёт человекочитаемую «полку».
- Логическое разделение «действующее / историческое» на уровне путей проще для навигации, чем git-археология.
- KCS-практика Archived и ISO-практика transfer-to-archive существуют именно потому, что состояние «restorable, вне поиска» полезно и отлично и от активного, и от удалённого.

**Условия применимости:**
- `archive/` ОПРАВДАНА, если: (а) исторические документы регулярно нужны людям/агенту для чтения; (б) есть надёжный механизм исключения `archive/` из активного контекста агента (per-folder CLAUDE.md с инструкцией «не читать `archive/` кроме явного запроса», исключение из README-индексов, `type: archived` во frontmatter).
- `archive/` ИЗБЫТОЧНА, если: документы после вывода из обращения практически не читаются людьми → достаточно `git rm` + запись в лог решений о том, что и почему удалено.

**Известные способы отказа:**
- Вариант «только git»: failure mode — человек в Obsidian не находит прецедент, воссоздаёт заново (потеря институциональной памяти); агент не знает, что решение когда-то принималось. Митигация: append-only лог решений (`decisions/`) как индекс того, что искать в git.
- Вариант «archive/»: failure mode — агент/человек находит и применяет устаревшее (главный риск); `archive/` незаметно превращается в свалку. Митигация: обязательный `status: archived/superseded` + баннер + явное исключение из индексов и из зоны чтения агента + периодическая машинная проверка, что в `archive/` нет документов без `superseded_by`/`replaced_by`.

**Рекомендация: не заводить `archive/` как директорию по умолчанию.** Использовать `git rm` + append-only `decisions/`-лог для ~90% случаев. Ввести `archive/` точечно и только для класса «историческое, но человеко-читаемое», обязательно с машинно-проверяемым исключением из активного контекста агента (per-folder CLAUDE.md + frontmatter `type` + отсутствие в README-индексах). Для документов, которые устарели, но остаются в активном дереве по другим причинам, — не архив, а deprecation-баннер + `status` + noindex-эквивалент (исключение из README-индекса).

## Caveats
- Количественные цифры о «стоимости» (Stripe: 17 ч/нед и ~$85 млрд/год; runbook-инцидент ~$120k) — из индустриальных/практических источников, не рецензируемых; трактовать как иллюстрацию порядка величины. Атрибуция $85 млрд именно документации — интерполяция сторонних блогов; в оригинале Stripe/Harris Poll это техдолг («maintenance issues», «bad code») в целом.
- Дискретное «39% = устаревание» не приведено в статье Aghajani et al. дословно как единая цифра — это распространённая вторичная формулировка; в первоисточнике up-to-dateness фигурирует как одна из категорий содержания в таксономии из 162 типов. Использовать осторожно.
- Данные о «freshness» из SEO-источников (Google ranking, AI citations) сознательно исключены как нерелевантные внутреннему repo-контексту — они про внешнюю видимость, а не про актуальность знаний.
- KCS, ISO 15489, ADR-практики валидированы в организационном контексте (поддержка, records management, инженерные команды); перенос на single-user repo с LLM-агентом — экстраполяция, требует проверки на практике.
- Практики LLM-поддержки документации (structured-MADR, README-maintenance) молодые (2024–2026), устойчивых лонгитюдных данных об их эффективности нет.
- Конкретные пороги (180/365 дней, 20% файлов, N месяцев) — разумные дефолты по аналогии с Google/Confluence-практикой, а не измеренные оптимумы; калибровать под темп изменения каждого домена.
