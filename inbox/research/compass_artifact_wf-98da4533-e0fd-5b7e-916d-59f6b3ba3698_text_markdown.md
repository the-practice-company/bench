# Полевой обзор: как устроены репозитории для агентов на практике

## TL;DR
- **Сходимость к общему формату состоялась на уровне имени и синтаксиса файла (AGENTS.md как открытый стандарт, >60 000 репозиториев, нативная поддержка в 20+ инструментах), но НЕ на уровне содержания: эмпирика (ETH Zürich, AGENTbench, 138 задач) показывает, что контекст-файлы «не улучшают долю решённых задач и при этом удорожают вывод более чем на 20%» — сильнейшая сложившаяся конвенция одновременно является и сильнейшим предметом обоснованной критики.**
- **Для некодового домена заказчика (Obsidian-vault + Claude Code, «Life OS», база знаний) уже существует узнаваемый корпус независимых реализаций, и они независимо сошлись к структуре, почти совпадающей с гипотезой заказчика: core/inbox/projects/areas/knowledge + boot-файл + слой памяти + прогрессивное раскрытие через README-индексы. Это самый ценный и самый прямой ориентир.**
- **Главное ограничение заказчика («человек — узкое место, что не проверяется машиной — деградирует») подтверждается всеми долгоживущими практиками: файлы состояния/памяти протухают, если их обновление лежит на человеке; работающие конвенции — те, где обновление делает агент по хуку/рутине, а декларативные правила заменены детерминированными проверками.**

## Ключевые находки (с уровнями свидетельства)

Уровни: **(а)** наблюдаемая частотность в репозиториях · **(б)** описанный опыт эксплуатации с указанием срока · **(в)** аргументированная позиция практика · **(г)** рекомендация вендора · **(д)** единичное влиятельное мнение.

1. **Формат инструктивного файла устоялся, содержание — нет.** AGENTS.md формализован как открытый стандарт в августе 2025 в коллаборации OpenAI, Google, Cursor, Factory и Sourcegraph; выпущен OpenAI и в конце 2025 передан в Linux Foundation Agentic AI Foundation (AAIF, к маю 2026 >170 организаций-членов) вместе с MCP (Anthropic) и Goose (Block). Более 60 000 репозиториев, нативная поддержка в 20+ инструментах (Codex, Cursor, Copilot, Gemini CLI, Aider, Windsurf, Zed, Factory, Jules и др.) **(а/г)**. Но крупнейшее эмпирическое исследование структуры (arXiv:2511.12884, «Agent READMEs», 2 303 файла из 1 925 репозиториев по Claude Code, Codex, Copilot) показывает отсутствие стандартного шаблона: файлы варьируются от 20 строк до 329 строк/74 секций **(а)**.

2. **«Больше контекста» эмпирически вредит.** ETH Zürich (Gloaguen, Mündler, Müller, Raychev, Vechev, «Evaluating AGENTS.md», arXiv:2602.11988, 12–13 февраля 2026; AGENTbench = 138 задач из 12 Python-репозиториев, выведенных из 5 694 реальных PR; модели Claude Sonnet 4.5, GPT-5.2, GPT-5.1 mini, Qwen3-30B): контекст-файлы «не дают улучшения доли решённых задач и при этом повышают стоимость вывода более чем на 20%»; LLM-сгенерированные файлы дают −3%, написанные человеком — лишь +4%; агенты следуют инструкциям слишком буквально **(а/б)**. Факторный анализ McMillan (arXiv:2605.10039, 1 650 сессий Claude Code, 16 050 наблюдений) не нашёл влияния размера/позиции/архитектуры файла на соблюдение после поправки на множественность, но зафиксировал падение соблюдения внутри сессии **(а)**.

3. **llms.txt как практика провалилась.** Ни один крупный вендор не подтвердил чтение в проде; Google прямо отказался (Gary Illyes, John Mueller сравнил с дискредитированным meta-keywords). Адоптация ~10% доменов (SE Ranking, 300 000 доменов), доля обращений AI-ботов ничтожна (Ahrefs: 97% из 137 000 файлов llms.txt никем не читаются; OtterlyAI: 84 обращения из 62 100 визитов AI-ботов) **(а/г)**.

4. **Прогрессивное раскрытие — единственная конвенция с согласием между вендором, эмпирикой и практикой.** Agent Skills (SKILL.md, трёхуровневая подгрузка) стали открытым стандартом в декабре 2025 **(г)**; принцип «минимум высокосигнальных токенов + подгрузка по требованию» — центральный тезис инженерного блога Anthropic **(г/в)**.

5. **Некодовый домен: независимая сходимость структуры.** Множество публичных Obsidian+Claude репозиториев независимо пришли к: boot-файл (CLAUDE.md) отдельно от контента, индекс-файл вершины (VAULT-INDEX.md), PARA-подобные директории, слой памяти в markdown без векторной БД **(а/б)**.

## Детали

### 1. Каталог конвенций

**КОНВЕНЦИЯ: единый корневой инструктивный файл (AGENTS.md / CLAUDE.md).**
Что решает: даёт агенту предсказуемое место для контекста и правил, читается автоматически в начале сессии.
Распространённость (трек А): очень высокая. AGENTS.md — открытый стандарт (>60 000 репозиториев; напр. репозиторий OpenAI Codex использует 88 файлов AGENTS.md по дереву каталогов). CLAUDE.md — нативный формат Claude Code с иерархической загрузкой, @import, path-scoped rules. Медианные размеры (arXiv:2511.12884): Copilot 535 слов, Claude Code 485, Codex 335,5. Структура почти всегда: один H1, 6–7 H2, 11–12 H3; глубокое вложение (H5+) редко. Читаемость низкая (FRE Claude 16,6 — «очень трудно»). Контент-анализ: build/run-команды 62,3%, детали реализации 69,9%, архитектура 67,7%, а security и performance лишь по 14,5% (значимый провал по non-functional требованиям). Файлы эволюционируют как конфиг: частые мелкие добавления, редкие удаления **(а)**.
Обоснование (трек Б): «включай только то, что верно в каждой сессии»; фронтир-модели надёжно исполняют ~150–200 инструкций, из которых системный промпт Claude Code уже съедает ~50 (HumanLayer) **(в)**. Anthropic добавила в дефолтный системный промпт инструкцию частично игнорировать CLAUDE.md — потому что пользователи забивали файл неуниверсальными «хотфиксами» (HumanLayer) **(в/г)**.
Уровень свидетельства: **(а)** для формы, **(б/в)** для рекомендаций по объёму.
Применимость к некодовому домену: прямая — это и есть «навигационный корень» заказчика. Но эмпирика требует держать его коротким (обычно называют цифры порядка 100–200 строк).
Совпадение с гипотезой заказчика: полное (CLAUDE.md как корень).

**КОНВЕНЦИЯ: минимализм инструкций / «signal density».**
Что решает: context rot и буквальное следование шумным инструкциям.
Распространённость (трек А): декларируется массово, но нарушается — медианные файлы велики и растут только вверх **(а)**.
Обоснование (трек Б): ETH Zürich — лишние требования делают задачи труднее; LLM-файлы часто лишь дублируют README (при удалении README они внезапно давали +2,7%) **(а/б)**. Codex CLI молча обрезает AGENTS.md >32 KiB — прямой аргумент за краткость **(б)**. Контекст-подложка: Chroma «Context Rot» (июль 2025, 18 фронтир-моделей) — надёжность падает нелинейно задолго до заполнения окна, деградация видна уже на 50k токенов при окне 200k **(б)**.
Уровень: **(а/б)** — редкий случай, где есть измерения.
Применимость: высокая. Некодовые vault-репозитории склонны к раздуванию описаний ещё сильнее кодовых.
Конфликт с гипотезой: гипотеза заказчика (README-индексы в каждой папке) хороша ТОЛЬКО если индексы короткие и подгружаются лениво, иначе она воспроизводит именно ту болезнь, что измерил ETH.

**КОНВЕНЦИЯ: прогрессивное раскрытие (skills, вложенные файлы, @-импорты, индексы).**
Что решает: ограничение внимания на длинном контексте.
Распространённость (трек А): растёт быстро. Agent Skills: метаданные (~100 токенов) в старте, тело по срабатыванию, вложенные файлы по требованию; официальный набор Anthropic (17 skills) — тело 275–8000 токенов, медиана ~2000, все метаданные вместе ~1700 токенов **(а/г)**. Вложенные CLAUDE.md/AGENTS.md подгружаются при доступе к директории; @import в CLAUDE.md с лимитом вложенности (до 5 уровней) **(г)**.
Обоснование (трек Б/В): инженерный блог Anthropic — «just-in-time» контекст, лёгкие идентификаторы (пути, запросы), подгрузка через инструменты; Claude Code — гибрид: CLAUDE.md грузится наперёд, glob/grep достают файлы по требованию **(г/в)**.
**Расхождение треков (важно):** декларируется, что вложенные инструкции доходят до агента, но есть свидетельства обратного — баг-репорт anthropics/claude-code #2571: вложенные CLAUDE.md не подгружаются автоматически при доступе к файлам в под-директории; Cursor-форум: агент игнорирует правило в под-директории (.mdc), обходной путь — переименовать в .md; @-импорты ломаются молча при переносе файла, tilde-expansion (@~/…) ненадёжен (#8765) **(б)**. То есть «агент дошёл до второго уровня» — НЕ гарантировано и требует проверки.
Уровень: **(г)** для механизма, **(б)** для отказов.
Применимость: высочайшая — это ядро рецепта заказчика. Но второй уровень нужно делать «притягиваемым» явной инструкцией в корне, а не рассчитывать на автоматику.

**КОНВЕНЦИЯ: слой памяти между сессиями (state / handoff / decision log).**
Что решает: отсутствие памяти у stateless-сессий.
Распространённость (трек А): устойчивый набор имён — HANDOVER.md, SESSION_LOG.md, state.md, DECISION_MEMORY.md, «two-file pattern» (постоянный CLAUDE.md + меняющийся HANDOVER.md); Claude Code имеет нативную auto-memory (MEMORY.md, грузятся первые 200 строк, детальные топик-файлы по требованию) **(а/г)**.
Обоснование (трек Б): практики с эксплуатацией месяцами (J.D. Hodges, Artem): память ассистента хороша для широких предпочтений, но не держит детальное состояние проекта (что тестировали, что упало, какие решения открыты); к записям HANDOVER возвращаются «недели спустя, чтобы вспомнить почему» **(б)**.
Уровень: **(б/в)**.
Применимость: прямая — это «лог решений + state.md» заказчика.
Ключевой риск сопровождения: протухание. Работающие варианты — где обновление делает агент (auto-memory, /remember, хук авто-коммита), а не человек.

**КОНВЕНЦИЯ: изоляция рабочих копий для параллельных агентов (git worktrees).**
Что решает: конфликтные правки при нескольких агентах.
Распространённость (трек А): широкая в кодовом домене; Claude Code имеет нативный `--worktree` и `isolation: worktree` для субагентов **(а/г)**.
Обоснование (трек В): изоляция на уровне инфраструктуры вместо координации агентов; практический потолок 4–5 параллельных агентов (RAM/CPU); stateful-инструменты (общая БД/MCP) всё равно сталкиваются **(в/б)**.
Применимость к некодовому домену: **низкая/средняя.** Для vault заказчика реальнее не параллельные writer-агенты, а «single-writer + read-only субагенты» (см. Cognition). Показателен паттерн claude-obsidian: «параллельные агенты не могут гонять vault; воркеры возвращают черновики, один оркестратор проверяет и применяет одну восстановимую транзакцию».

**КОНВЕНЦИЯ: спецификация как источник истины (spec-driven).**
Что решает: «vibe-coding» без критериев приёмки.
Распространённость (трек А): звёзды высокие — Spec Kit ~124k (11k форков, активная разработка, 55+ релизов с конца февраля 2026), OpenSpec ~62k, BMAD-METHOD ~51k (v6-переписка, 2k коммитов); все активно поддерживаются мейнтейнерами **(а)**.
**Расхождение треков (сильное):** высокие звёзды маскируют паттерн «попробовал недели → откатился к обычному промптингу». Colin Eberhardt (CTO Scott Logic, 26 ноября 2025): SDD-путь дал 689 строк кода при 2 577 строках markdown (33m30 agent-времени + 3,5 ч ревью), тогда как обычный iterative prompting — ~1000 строк за 8 мин agent-времени и ~24 мин ревью; verbatim: «I am a lot more productive without SDD, around ten times faster» **(в/б)**. GitHub Discussion #1784 (NaikSoftware, эксплуатация несколько месяцев, реальный мультимодульный проект): «SpecKit лишь усложняет работу… в большинстве случаев я откатываю всё и работаю без него», тот же опыт с Kiro и BMAD («застрял в сотнях спек») **(б)**. Центральный неустранённый провал — spec drift (спека расходится с реальностью), признаётся даже сторонниками; Kiro «пока не автоматизирует синхронизацию spec↔code» **(в)**.
Уровень: **(а)** для звёзд, **(в/б)** для откатов.
Применимость: **средняя.** Формальные критерии приёмки полезны для «projects/ с критерием завершённости», но полновесный SDD-пайплайн для базы знаний — избыточен. Практический консенсус даже у сторонников: «2–3 предложения → обычная автоматизация; крупная фича → Spec-Kit».

### 2. Карта разногласий

| Спор | Позиция A | Позиция B | Сильнейший аргумент | От чего зависит выбор | Куда склоняется случай заказчика |
|---|---|---|---|---|---|
| Объёмный vs минимальный инструктивный файл | «документируй всё» | «под 150–200 строк» | Эмпирика ETH/McMillan на стороне минимализма; больше контекста ≠ лучше | Стабильность правил, зрелость домена | **Минимальный корень + ленивые индексы** |
| Декларативные правила vs исполняемые процедуры/навыки/хуки | правила в markdown | skills + детерминированные хуки | «инструкции — совет, хуки — гарантия»; Claude Code трактует память «как контекст, а не как enforced-конфиг» | Критичность правила | **Хуки для «must-happen», skills для процедур** |
| Управление спецификацией vs разговорный режим | spec-driven | iterative prompting | 10x-замер Eberhardt против; но SDD помогает на крупных фичах | Размер и повторяемость задачи | **Критерии приёмки да, тяжёлый SDD-пайплайн нет** |
| MCP vs CLI/скрипты | протокол | shell + skills | CLI в 10–32x токен-эффективнее (Arize, Zilliz); GitHub MCP грузит ~55k токенов схемы наперёд; Perplexity/Garry Tan публично деприоритизировали MCP | Удалённость/проприетарность инструмента, нужен ли OAuth/аудит | **CLI/скрипты + skills; MCP точечно (напр. семантический поиск)** |
| Один длинный контекст vs субагенты | single-threaded (Cognition) | multi-agent (Anthropic) | Cognition: «writes single-threaded», конфликтующие неявные решения ломают результат; Anthropic: многоагентная (Opus 4 lead + Sonnet 4 субагенты) превзошла одиночный Opus 4 на 90,2% на research-eval, но ~15x токенов | Независимость подзадач | **Один writer + read-only субагенты** |
| Состояние в файлах репо vs внешнее хранилище (вектор/memory-сервер) | markdown в git | векторная БД | «no vector database, just markdown» — портируемость, git-история; но семантический поиск слабее на больших vault | Размер корпуса, потребность в семантике | **Файлы+git как истина; опц. локальный индекс (QMD) поверх** |

### 3. Что заказчик проектирует заново, хотя конвенция уже есть (рекомендую принять ради совместимости с обученным поведением моделей)

- **Имя boot-файла.** Модели натренированы искать CLAUDE.md (Claude Code) и AGENTS.md. Гипотеза заказчика (CLAUDE.md-корень) уже совместима — не изобретать своё имя. Для кросс-инструментальности держать AGENTS.md как тонкий указатель на CLAUDE.md.
- **Прогрессивное раскрытие через SKILL.md.** Фоновые рутины обслуживания заказчика — это ровно паттерн Agent Skills (формат-стандарт, декабрь 2025). Оформлять рутины как skills, а не как разделы гигантского CLAUDE.md.
- **Boot-файл отдельно от контента + индекс вершины.** Паттерн ai-memory-vault (CLAUDE.md вне vault как «boot config» с идентичностью и правилами — переживает компакцию; VAULT-INDEX.md внутри как «operating manual» — карта vault, может не пережить компакцию) решает ту же задачу, что README-индексы заказчика. Принять это разделение.
- **PARA/areas-projects как таксономия.** projects (с критерием завершённости) / areas (без даты) — это буквально PARA Тиаго Форте; independent Life-OS репозитории (LifeOS-OSS, PAI, obsidian-claude-pkm) уже сошлись к нему. Не изобретать свою.
- **Слой памяти именами HANDOVER/state/decision-log** — устоявшийся словарь, модели видели его в обучении.

### 4. Где сложившихся конвенций нет — решать самому

- **Как гарантировать, что агент реально доходит до второго уровня.** Автоподгрузка вложенных файлов ненадёжна (баги anthropics/claude-code #2571, Cursor-форум). Конвенции проверки нет — заказчику нужен собственный механизм (явные ссылки в корне + периодический self-check/eval).
- **Борьба с протуханием state в некодовом домене.** В коде помогают тесты/линтеры; для базы знаний детерминированной проверки «свежести» нет. Заказчику проектировать свои машинные проверки (даты во frontmatter, хук-валидатор, авто-архивация).
- **archive/ — под вопросом.** Единого мнения нет; часть репозиториев держит Archives/ (obsidian-claude-pkm), часть обходится статусами во frontmatter. Решение за заказчиком (склоняюсь к статусу-полю вместо отдельной папки — меньше ручной дисциплины).
- **Два представления (человек/агент) одного знания.** Практика поддержания двух копий признана дорогой (стоимость расхождения); llms.txt-опыт показал бесполезность «отдельного представления для машины», если оно не поддерживается. Для Obsidian заказчика вывод: одно markdown-представление и для человека, и для агента — не плодить второе.
- **Табличные коллекции (.base).** Конвенций под агентную работу с Obsidian Bases нет — зона самостоятельного проектирования (пока распространён Dataview-запрос как «представление», которое агент затем анализирует — Kenneth Reitz).

## Рекомендации

**Этап 1 — фундамент (принять готовые конвенции):**
1. CLAUDE.md-корень ≤150 строк: идентичность субъекта, жёсткие правила (императивами: «NEVER…», «Use X» вместо «we generally prefer»), карта верхнего уровня ссылками (не прозой). AGENTS.md — тонкий указатель для кросс-совместимости.
2. Индекс-файл вершины (VAULT-INDEX.md) отдельно от boot-файла: правила и идентичность — в корне (переживают компакцию), карта vault — в индексе.
3. Таксономия core/inbox/projects/areas/knowledge/sources/tmp принимается как есть — совпадает с PARA и с полевыми примерами.

**Этап 2 — память и рутины (машина, не человек):**
4. Слой памяти: state.md (текущее положение) + decision-log (ADR-подобный, только решения+обоснование) + auto-generated журнал. Обновление — по хуку/skill в конце сессии, НЕ вручную.
5. Фоновые рутины — как SKILL.md с прогрессивным раскрытием, не как разделы CLAUDE.md.
6. Критичные инварианты — как хуки (детерминированные, PreToolUse), а не строки в правилах: память Claude Code трактуется «как контекст, а не как enforced-конфиг».

**Этап 3 — масштабирование:**
7. Инструменты: shell/скрипты + skills по умолчанию; MCP только для семантического поиска по большому vault (напр. локальный индекс QMD как MCP-сервер).
8. Мультиагентность: single-writer + read-only субагенты для сбора контекста; git worktrees только если появятся реально независимые пишущие задачи.

**Пороги, меняющие решения:** если CLAUDE.md перевалил ~200 строк или агент начал игнорировать ранее исполнявшиеся правила — резать и выносить в ленивые индексы. Если grep/glob перестаёт находить нужное на большом vault — добавлять семантический индекс (не раньше). Если ручное обновление state пропускается — переносить на хук.

## Оговорки
- Практикам <2 лет, лонгитюдных данных нет; все spec-driven инструменты моложе ~11 месяцев — «заброшенность на дистанции» пока недоказуема, доступен лишь паттерн «попробовал недели → откатился».
- Часть эмпирики (ETH, McMillan, Chroma) измерена на КОДОВЫХ задачах; перенос выводов на базу знаний — обоснованная экстраполяция, но не прямое измерение. При этом направление выводов (краткость, прогрессивное расклытие, протухание state) согласуется с опытом vault-практиков.
- Высокие звёзды репозиториев ≠ живое использование; markdown-«best practices»-посты часто эхо одного тезиса (HumanLayer, инженерный блог Anthropic) — учтён первоисточник, а не перепечатки.
- Многие некодовые репозитории — свежие и авторские; признаки живого стороннего использования (форки, свежие коммиты, /upgrade-механики) есть у obsidian-claude-pkm, LifeOS/PAI, obsidian-skills (Steph Ango, CEO Obsidian — 14 900 звёзд за <3 месяца), но у части — только демонстрационные.
- Отдельные числа адоптации (>60 000 репозиториев AGENTS.md, звёзды Spec Kit/OpenSpec/BMAD) взяты из вторичных сводок и пресс-материалов на дату исследования и подвержены быстрому устареванию; проверять по первоисточнику перед принятием решений.
